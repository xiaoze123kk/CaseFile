# CaseFile 数据库迁移职责说明

本目录维护 PostgreSQL 18 的个人版数据库结构。Alembic migration 是结构事实来源，`backend/src/casefile/data_postgres/models/` 的 SQLAlchemy metadata 必须与唯一 head 一致。

## 当前五段基线

```text
V20260726131010  users + projects
        ↓
V20260726131012  casefiles + drafts + casefile_objects + casefile_refs + draft_operations
        ↓
V20260726131014  entities + people + locations + events + information_units
                 + evidence_items + testimonies
        ↓
V20260726131017  narrative_phases + claims + hypotheses + reasoning_paths
                 + reasoning_nodes + reasoning_edges + resolution_specs
                 + resolution_slots + casefile_constraints + knowledge_states
                 + knowledge_state_entries
        ↓
V20260726131019  draft_snapshots + canon_versions + audit_events
                 + 循环外键 + 全部数据库函数与触发器
```

最终恰好 28 张业务表。所有主键为 `BIGINT GENERATED BY DEFAULT AS IDENTITY`，关系外键均为 `BIGINT`；不使用 UUID 或 `public_id`。唯一的稳定字符串领域 ID 是 `casefile_objects.object_id`。迁移文件名必须保持大写 `V`、Asia/Shanghai 真实 14 位时间戳和单头单链。

本基线只面向个人产品。不存在 Workspace、Membership、成员、邀请、团队角色、评论、Review Task、共享项目或团队预算的表、列、约束、触发器和种子数据。

## 存储分层

```text
casefile_objects（稳定身份、类型、revision、来源）
          │ 1:1
          ▼
专用当前态表（规范化字段，Draft 唯一事实源）
          │
          ├── 单值关系：带 project/casefile/draft 的复合外键
          └── 多值关系：casefile_refs（ordinal + metadata_jsonb）
          │
          ▼
draft_snapshots（完整不可变 JSON）
          │ 0..1
          ▼
canon_versions（所有者确认的完整不可变 JSON）
          │
          └── audit_events（独立审计，不参与内容哈希）
```

`casefile_objects` 不含 `payload_jsonb`。JSONB 只允许用于开放叶子结构、Operation 前后值、完整 Snapshot/Canon 和审计摘要；身份、状态、revision 及引用必须使用正式关系列。

未来 Snapshot Builder 的 CaseFile JSON 顶层固定为：`casefile`、`narrative_phases`、`entities`、`events`、`information_units`、`claims`、`hypotheses`、`reasoning_paths`、`resolution_spec`、`constraints`、`knowledge_states`。Person/Location 作为 Entity 具体类型输出，Evidence/Testimony 作为 Information Unit 具体类型输出；数据库内部 BIGINT 不替代契约中的稳定字符串 `object_id`。

## 逐表职责、写入方和生命周期

下表“写入方”是后续 Repository/Service 必须遵守的边界，本轮只建立数据库底座。

| 表 | 职责与主要关系 | 计划写入方 | 生命周期 |
|---|---|---|---|
| `users` | 个人账号主体，不含认证凭证。 | 未来账号服务。 | 展示名/状态可改；被项目或历史引用后不物理删除。 |
| `projects` | 单一 `owner_user_id` 的个人聚合根。 | Project Repository。 | 可编辑/归档；所有权不可转移。 |
| `casefiles` | Project 唯一 CaseFile，保存 Schema 版本和当前 Canon 指针。 | CaseFile Repository；Canon 触发器。 | 元数据可改/归档，版本历史不覆盖。 |
| `drafts` | CaseFile 唯一当前 Draft，保存整体 revision 和基准 Canon。 | Draft Repository；Operation/Canon 触发器。 | 单行持续编辑；`locked` 时拒绝 Operation。 |
| `casefile_objects` | 轻量对象注册表；稳定 `object_id`、核心类型、来源、置信度和确认状态。 | Draft Repository。 | 当前态可改；身份/类型不可变；软删除后 ID 不复用。 |
| `casefile_refs` | 同 Draft 多值跨类型引用边，保存字段路径、类型、顺序和边元数据。 | 引用写入器，与内容同事务。 | 当前态可重建；已知端点类型受触发器约束。 |
| `draft_operations` | 有序增量编辑日志和乐观锁输入。 | Draft 编辑事务。 | 只追加，触发器原子推进 Draft revision。 |
| `narrative_phases` | 有序叙事阶段、发布规则和状态。 | Narrative Repository。 | 当前 Draft 内可增改；顺序唯一。 |
| `entities` | Person/Location/Organization/Object/Concept 等通用实体基类。 | Entity Repository。 | 当前态可增改；`entity_kind` 不可变。 |
| `people` | `entities` 的 Person 1:1 扩展，保存角色与背景。 | Entity Repository。 | 与 Person Entity 同生共存。 |
| `locations` | `entities` 的 Location 1:1 扩展，保存 geo 与移动规则。 | Entity Repository。 | 与 Location Entity 同生共存；相邻关系写引用边。 |
| `events` | 时间、叙事顺序、阶段、地点、可见性与真值状态。 | Event Repository。 | 当前态可编辑；Actor 为多值引用边。 |
| `information_units` | Evidence/Testimony/Document 等信息基类。 | Information Repository。 | 当前态可增改；`information_kind` 不可变。 |
| `evidence_items` | Evidence 1:1 扩展，保存证据类型和来源 Event。 | Information Repository。 | 与 Evidence Information Unit 同生共存。 |
| `testimonies` | Testimony 1:1 扩展，保存说话人、原文和暂存音频引用。 | Information Repository。 | 与 Testimony Information Unit 同生共存。 |
| `claims` | 可被支持或反驳的断言及判定状态。 | Claim Repository。 | 当前态可编辑；证据关系写引用边。 |
| `hypotheses` | 候选解释、得分和排除规则。 | Hypothesis Repository。 | 当前态可编辑；Claim/Information 关系写引用边。 |
| `reasoning_paths` | 一条命名推理路径的类型、状态、置信度和人工确认。 | Reasoning Repository。 | 当前态可编辑；拥有 Node/Edge。 |
| `reasoning_nodes` | Path 内稳定 `node_key`、顺序、来源对象和陈述。 | Reasoning Repository。 | 随 Path 编辑；key/顺序在 Path 内唯一。 |
| `reasoning_edges` | 同 Path 两个 Node 间的有向论证边。 | Reasoning Repository。 | 随 Path 编辑；禁止跨 Path 和自环。 |
| `resolution_specs` | 每个 Draft 唯一的动态结论规格。 | Resolution Repository。 | 当前态可编辑；每 Draft 最多一行。 |
| `resolution_slots` | Spec 内稳定 `slot_key`、顺序、必填标志和动态值。 | Resolution Repository。 | 随 Spec 编辑；key/顺序唯一。 |
| `casefile_constraints` | 可选目标对象上的硬/软规则与冲突状态。 | Constraint Repository。 | 当前态可启停和解决冲突。 |
| `knowledge_states` | Entity 在 Narrative Phase 的总体知识状态。 | Knowledge Repository。 | Entity/Phase 组合在 Draft 内唯一。 |
| `knowledge_state_entries` | 某 Information Unit 的认知、披露、获得来源和确定度。 | Knowledge Repository。 | 随 Knowledge State 编辑；顺序唯一。 |
| `draft_snapshots` | 指定 Draft revision 的完整 CaseFile JSON、Schema 和 SHA-256。 | Snapshot Service。 | 每 revision 最多一行；不可更新/删除。 |
| `canon_versions` | 所有者确认的连续正式版本，来源 Snapshot 且保存完整 JSON。 | Canon Service。 | 每次确认追加；不可更新/删除。 |
| `audit_events` | 项目关键动作的 Actor、目标、Trace 和结构化摘要。 | Audit Port；Canon 完成触发器。 | 只追加；独立于 Canon 内容和哈希。 |

## 关系与数据库门禁

- Project : CaseFile = 1:1，CaseFile : 当前 Draft = 1:1。
- 所有专用当前态表携带 `project_id`、`casefile_id`、`draft_id`，复合外键拒绝跨 Project、CaseFile 和 Draft 串联。
- 核心专表的 `object_registry_id` 必须对应正确 `casefile_objects.object_type`。
- `people` 只接受 `entity_kind=person`，`locations` 只接受 `location`；`evidence_items` 只接受 `information_kind=evidence`，`testimonies` 只接受 `testimony`。
- 已知引用 `event_actor`、`location_adjacent_to`、`supports`、`refutes`、`hypothesis_claim`、`hypothesis_required_information` 由触发器校验端点；自定义引用留给未来 Schema Validator。
- Event → Location/Phase、Evidence → Source Event、Testimony → Speaker Person、Knowledge → Entity/Phase/Information、Reasoning Node → 来源对象、Constraint → 目标对象均使用正式复合外键。
- Draft Operation 插入锁定 Draft，校验 `base_revision`、连续 `sequence_no`、个人所有者 Actor，并原子推进 revision。
- Snapshot 插入锁定 CaseFile/Draft，要求当前 revision、项目所有者和三层 Schema 一致。
- Canon 插入锁定 CaseFile/Draft，要求来源 Snapshot、内容/哈希、所有者、父版本、连续版本号和四层 Schema 一致；完成后更新两个 Canon 指针并追加 Audit。

### Schema 四层门禁

```text
casefiles.schema_version
  = drafts.schema_version
  = draft_snapshots.schema_version
  = canon_versions.schema_version
```

应用使用 RFC 8785 规范化完整 JSON，对 UTF-8 字节计算 SHA-256。数据库验证 64 位小写十六进制格式，并要求 Canon JSON/哈希与来源 Snapshot 完全相同；数据库不在触发器中组装 Snapshot。

## 触发器分组

| 分组 | 作用 |
|---|---|
| `trg_*_updated_at` | 维护 23 张可变表的 `updated_at`。 |
| owner/object/discriminator immutable | 禁止项目所有权、对象稳定身份/类型、Entity/Information 判别类型被普通 UPDATE 改写。 |
| `trg_*_registered_type` | 验证 10 张核心专表与对象注册类型一致。 |
| subtype triggers | 验证 Person/Location/Evidence/Testimony 的基类判别类型。 |
| `trg_casefile_refs_known_type` | 验证六类已知引用的方向、端点类型和 Location 自环。 |
| Operation/Snapshot/Canon gates | 完成 revision 乐观锁、Schema/所有者/内容门禁、Canon 指针与审计事务。 |
| `trg_*_immutable` | 禁止 `draft_operations`、`draft_snapshots`、`canon_versions`、`audit_events` 普通 UPDATE/DELETE。 |

Operation、Snapshot 与 Audit 的职责不同：Operation 是“如何编辑”的增量日志；Snapshot 是“某个 revision 的完整候选输入”；Audit 是“谁在何时对哪个业务目标做了什么”的责任摘要。三者不能互相替代。

## 明确延后

本轮不创建 Validator Report、Export Manifest、Task、Patch、Simulation、Compiler、预算、删除工作流、Asset、认证凭证、全文/向量投影，以及任何 Workspace、Membership 或团队协作表。
