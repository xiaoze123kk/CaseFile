# CaseFile 数据库迁移职责说明

本目录维护 PostgreSQL 18 的个人版数据库结构。Alembic migration 是结构事实来源，`backend/src/casefile/data_postgres/models/` 的 SQLAlchemy metadata 必须与唯一 head 一致。

## M3.8-00 冻结的迁移契约（尚未实现）

M3.8 计划新增 `agent_goal_sessions`、`agent_goal_revisions`、`agent_goal_obligations`、`agent_goal_obligation_dependencies`、`agent_goal_deliveries`、`agent_goal_observations`、`agent_goal_task_runs`、`agent_goal_transitions` 八张表。精确状态机、关系、预算、不可变边界与 rollout 见 `docs/m3.8-goal-session-runtime.md`。

本节是 M3.8-00 设计冻结，不表示迁移已经存在。M3.8-01 之前当前唯一 head、ORM metadata 和正式业务表数量仍为 66；不得提前修改 foundation table-count 门禁。M3.8-01 必须使用真实 Asia/Shanghai 时间戳创建单链迁移，并在同一阶段同步 ORM、复合归属外键、部分唯一索引、终态不可变触发器、旧 head 升级测试和本文的正式基线/逐表职责。

最终恰好 66 张业务表。所有主键为 `BIGINT GENERATED BY DEFAULT AS IDENTITY`，关系外键均为 `BIGINT`；不使用 UUID 主键。CaseFile v1 的稳定字符串 ID 只保存在契约对象字段中；`briefs.public_id`、`casefiles.object_id` 和 `drafts.version_id` 是契约所需稳定 ID，不是关系主键。

本基线只面向个人产品。不存在 Workspace、Membership、成员、邀请、团队角色、评论、Review Task、共享项目或团队预算的表、列、约束、触发器和种子数据。认证/JWT 尚未实现；当前只存用户级模型 Provider 设置。

## 存储与生成分层

```text
user_provider_settings（用户级密文 API Key 与模型配置）
source_records（原稿、润色候选与人工修订；不可变）
        │
        ├── brief_intakes（可恢复阶段、revision 与当前指针）
        │       ├── brief_intake_questions（问题历史 + 回答状态）
        │       └── brief_intake_candidates（不可变候选与父子谱系）
        │                         │ 作者采用
        │                         ▼
        └────────────────── briefs（可变草稿） → brief_versions（确认后不可变）
                               │
                               ▼
task_runs（Brief/Intake 五类任务与 casefile_chat 的冻结输入）
        └── task_attempts（完整不可变候选）+ task_events（SSE 回放）
                               │
                               ├── Brief → Draft 成功：等待作者显式采用
                               │                         │
                               │                         ▼
agent_threads → agent_messages → casefile_chat TaskRun
                                  │
                                  └── agent_patch_sets → agent_patch_operations
                                                              │
                                                              ▼
casefile_objects（稳定身份、契约顺序、来源元数据）
          │ 1:1
          ▼
专用当前态表（规范化字段，Draft 唯一事实源）
          │
          ├── v1 ObjectRef：casefile_contract_refs
          ├── 旧版语义边：casefile_refs
          └── 生成事务：draft_operations + draft_snapshots
                              │
                              ▼
canon_versions（所有者确认的完整不可变 JSON）
          └── audit_events（独立审计，不参与内容哈希）

drafts ── exposure_plans（独立 revision 指针）
              └── exposure_plan_revisions（不可变完整版本）
                       └── exposure_plan_entries（线性顺序）
                                └── exposure_plan_entry_refs（稳定对象引用）

compiler_profiles（可变 current pointer）
        └── compiler_profile_versions（不可变 payload/schema/hash）
                         │ 显式选择
                         ▼
compile_runs（Build 身份与 Snapshot/Canon?/Exposure?/Profile 精确绑定）
        ├── task_runs（providerless novel_compile；权威冻结 Manifest 与执行状态）
        │       └── agent_step_runs（成功/失败/复用执行审计）
        └── compile_artifacts（Run 内唯一不可变 input_manifest / narrative_ir / novel_plan / scene_plan 产物）
```

`casefile_objects` 不含通用正文 `payload_jsonb`。JSONB 只承载契约中的结构化叶子、工具/用量/错误摘要、Operation 前后值和完整 Snapshot/Canon；身份、状态、revision、租约及引用使用正式关系列。

目标无关的 CaseFile v1 JSON 顶层不再包含 `project_profile` 和 `phases`；Resolution 使用 `reasoning_question`，不再保存 Target 公平性字段。数据库中的 `narrative_phases`、`resolution_specs.target_question` 与 `fairness_requirements_jsonb` 暂作为旧规范化模型的兼容列保留，不再投影到当前 1.0 JSON。数据库内部 BIGINT 不替代契约稳定字符串 ID；`casefile_contract_refs` 保存 ObjectRef 的 `object_type + object_id` 及其 JSON Pointer。

## 66 张表的职责、写入方和生命周期

| 表 | 职责与主要关系 | 写入方 | 生命周期 |
|---|---|---|---|
| `users` | 个人账号主体，不含登录凭证。 | 开发种子；未来认证服务。 | 状态可改；被业务引用后不物理删除。 |
| `projects` | 单一 `owner_user_id` 的个人聚合根。 | Project Service。 | 可编辑/归档/清空；所有权不可转移。 |
| `user_provider_settings` | 用户 + Provider 唯一的模型、预算、AES-256-GCM 密文密钥和配置版本；删除密钥后保留不含密文的墓碑行供历史 TaskRun 引用。 | Workflow Service。 | 可轮换或清空凭据；活动任务期间禁止删除；API 不回显密文或明文。 |
| `source_records` | Project 内不可变原始素材、Agent 润色候选和人工修订；复合外键约束父来源与生成 TaskRun 同属一个 Project。 | Workflow Service；Brief Intake Service；Worker。 | 只追加；原稿不被润色候选覆盖。 |
| `brief_intakes` | Project 唯一的建案聚合，保存乐观并发 revision、当前阶段、来源、问题任务、当前候选和已采用候选指针。 | Brief Intake Service。 | 单行持续演进；采用后保持正式 Brief 审阅态，旧项目首次读取时幂等初始化。 |
| `brief_intake_questions` | 每次问题 TaskRun 生成的 0–2 道问题历史及作者回答状态；定义与来源不可改写。 | Brief Intake Service；Worker。 | 只追加问题集；仅回答状态可更新；硬问题不可挂起。 |
| `brief_intake_candidates` | 结构化创作简报候选、输入哈希、父候选、Agent/人工来源和保存书签。 | Brief Intake Service；Worker。 | 候选正文与谱系只追加且不可变；仅保存书签字段可更新，过时候选保留但不可采用。 |
| `briefs` | Project 唯一目标无关 Brief 草稿及当前确认版本指针；Intake 采用在同一事务内投影候选。 | Workflow Service；Brief Intake Service。 | revision 乐观更新；内容变化后旧确认指针失效。 |
| `brief_versions` | 用户确认的 Brief 内容、连续版本号与 RFC 8785 哈希。 | Workflow Service。 | 只追加，不可更新/删除。 |
| `casefiles` | Project 唯一 CaseFile，保存项目级 v1 稳定 ID、Schema、非空 Current Draft 复合指针和当前 Canon 指针。 | Project/CaseFile Service；Canon 触发器。 | 元数据可改/归档；Current Draft 原子切换并写 Audit；历史不覆盖。 |
| `drafts` | CaseFile 下可有多份独立 Draft，分别保存文档标题/状态、v1 版本链字段、Brief 来源、revision 和基准 Canon。 | Draft/Generation Service。 | 独立持续编辑；已有正文后采用候选创建新行并设为当前；`locked` 时拒绝 Operation/激活。 |
| `casefile_objects` | v1 对象注册表；稳定 ID、契约顺序、来源、标签、置信度和确认状态；M3.4 兼容 `proposed` 状态。 | Draft/Generation Service。 | 当前态可改；身份/类型不可变，软删除后 ID 不复用；`object_id` 在 Draft 内唯一。 |
| `casefile_refs` | 兼容旧纵向切片的同 Draft 多值语义边。 | 旧版编辑服务。 | 当前态可重建；已知端点受触发器约束。 |
| `casefile_contract_refs` | v1 ObjectRef 的来源对象、字段 JSON Pointer、目标类型/稳定 ID 与顺序。 | v1 Generation/Projection。 | 随当前 Draft 原子重建；目标由契约 Validator 校验。 |
| `draft_operations` | 有序增量编辑日志和 revision 乐观锁输入；支持历史生成、候选显式采用、Agent 建议整批应用和整批撤销。 | Draft 编辑/Generation/Agent Patch 事务。 | 只追加，触发器推进 Draft revision。 |
| `exposure_plans` | 每个 Draft 唯一的线性披露计划主表，只保存独立 revision 和当前修订指针。 | Exposure Plan Service；Draft 插入触发器。 | 随计划保存推进自身 revision；不修改 Draft revision、Event.time 或 Canon。 |
| `exposure_plan_revisions` | 一次人工确认后的完整披露计划版本。 | Exposure Plan Service。 | 只追加，不可更新/删除；版本号在 Plan 内连续。 |
| `exposure_plan_entries` | 某计划修订内按 `sequence_no` 排列的披露节点、稳定 key、标题和可选说明。 | Exposure Plan Service。 | 随修订一次性追加；不可更新/删除。 |
| `exposure_plan_entry_refs` | 披露节点对同 Draft `casefile_objects` 的有序规范化引用。 | Exposure Plan Service。 | 随条目一次性追加；复合外键拒绝跨 Draft 引用，不可更新/删除。 |
| `exposure_plan_obligations` | 披露节点声明的 participant/basis/hypothesis 强类型规划义务及 hard/soft 层级。 | Exposure Plan Service。 | 随 v2 修订一次性追加；不可更新/删除。 |
| `exposure_plan_obligation_refs` | 语义义务对同 Draft `casefile_objects` 的有序规范化引用。 | Exposure Plan Service。 | 复合归属外键拒绝跨 Draft/Revision 引用，不可更新/删除。 |
| `narrative_phases` | 旧版 Phase 的顺序、发布规则、进入/允许动作/完成条件。 | 兼容投影。 | 当前 1.0 JSON 不再公开 Phase；表暂保留以避免同轮破坏性删表。 |

| `relationships` | v1 一等关系对象的标题、类型、方向、真值与可见性。 | v1 Generation/Projection。 | 与 `object_type=relationship` 注册行 1:1。 |
| `people` | 旧版 Person Entity 的 1:1 扩展。 | 旧版 Entity Service。 | 与 Person Entity 同生共存。 |
| `locations` | 同时支持旧版 Location Entity 扩展与 v1 独立 Location 对象；`geo_jsonb` 原样保存可选示意坐标或 WGS84 坐标。 | v1 Generation/Editing；旧版 Entity Service。 | `entity_id` 与 `object_registry_id` 二选一路径；空 `geo_jsonb` 投影为坐标字段省略。 |

| `information_units` | v1 信息类型、正文、可靠性、真值、分类、取得条件与发布状态。 | v1 Generation/Editing/Projection。 | 当前态可增改；仅存在旧 `evidence_items`/`testimonies` subtype 行时禁止修改判别类型。 |

## 关系与数据库门禁

- Project : CaseFile = 1:1；CaseFile : Draft = 1:N；CaseFile : Current Draft = 1:1；Project : Brief = 1:1；Project : SourceRecord = 1:N；Brief : BriefVersion = 1:N。
- Draft : Exposure Plan = 1:1；Exposure Plan : Revision = 1:N；Revision : Entry = 1:N；Entry : ObjectRef/PlanningObligation = 1:N；Obligation : ObjectRef = 1:N。Exposure Plan 仅用自身 revision 乐观并发，不参与 Draft/Canon 版本链。
- Project : CompilerProfile = 1:N；Profile : Version = 1:N；CompileRun 精确绑定一个 Snapshot、一个 Profile Version、一个 TaskRun，以及可选的同 Snapshot Canon 与 exact Exposure revision；Artifact 同时绑定 Run/Task/Step。
- 所有当前态专表携带 `project_id + casefile_id + draft_id`，复合外键拒绝跨归属串联。
- v1 生成可针对同一当前 BriefVersion 重复执行；成功只追加不可变候选。显式采用使用 `expected_current_draft_id` 指针门禁并校验冻结来源 Draft/revision；首次物化空 Draft，后续采用创建新 Draft。候选 JSON、目标 Draft 投影、Snapshot JSON 与 RFC 8785 哈希必须一致。
- `task_runs` 按任务类型固化 SourceRecord、Brief revision/version 或最新 CaseFile + Thread 消息上下文、输入哈希与 JSON、Provider/模型配置版本、Schema/Agent/Prompt/Toolset 版本和预算；Worker 通过 `FOR UPDATE SKIP LOCKED` 与 lease 领取。
- Agent 建议固定生成时的 Draft revision；人工可在任务运行期间继续编辑，旧 revision 的 PatchSet 标记 stale 并禁止应用。逐项决策保存在 PatchOperation，最终选择以一个 PatchSet 原子应用或整批撤销。
- `task_attempts` 保留每次候选、结构修复/Validator 错误和用量，非空候选写入后不可改写或删除；`task_events` 只公开阶段、工具摘要、Validator 和用量，不存隐藏思维链。
- Draft Operation 插入锁定 Draft，校验 `base_revision`、连续 `sequence_no`、个人所有者 Actor，并原子推进 revision。
- Snapshot 插入锁定 CaseFile/Draft，要求当前 revision、项目所有者和三层 Schema 一致。
- Canon 插入锁定 CaseFile/Draft，要求来源 Snapshot、内容/哈希、所有者、父版本、连续版本号和四层 Schema 一致；完成后更新两个 Canon 指针并追加 Audit。

### Schema 四层门禁

```text
casefiles.schema_version
  = drafts.schema_version
  = draft_snapshots.schema_version
  = canon_versions.schema_version
```

应用使用 RFC 8785 规范化完整 JSON，对 UTF-8 字节计算 SHA-256。数据库验证 64 位小写十六进制格式，并要求 Canon JSON/哈希与来源 Snapshot 完全相同；数据库不在触发器中组装 Snapshot。

Operation、Attempt、Event、Snapshot 与 Audit 职责不同：Operation 是“Draft 如何变化”；Attempt 是“一次执行发生了什么以及生成了哪份候选”；Event 是“可以安全回放给用户的阶段摘要”；Snapshot 是“某个已采用 Draft revision 的完整内容”；Audit 是“谁在何时执行了关键业务动作”。
