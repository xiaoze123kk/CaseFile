# M3.8 GoalSession Runtime 架构决策

状态：**M3.8-00 至 M3.8-06 已完成；M3.8-07 v1 已判定污染并冻结为无效；v2 私有 24×3 Pro 在 `bd16432`（57/72）、`523b603`（64/72）和 `b65dd66`（65/72）上均未取得资格，当前第三轮修复候选尚未重新取得资格**
冻结日期：2026-08-29
适用范围：CaseFile 后端 `casefile_chat`，不包含前端开发。

## 1. 决策摘要

M3.8 在 M3.7 Bounded Goal Harness 外增加持久化 `GoalSession`。`GoalSession` 负责跨消息和跨 `TaskRun` 的长期协作生命周期；`TaskRun` 继续表示一次输入、Provider、Prompt、工具集和预算均已冻结的执行切片。

```text
AgentThread
  └─ GoalSession
       ├─ GoalRevision 1
       │    └─ TaskRun slice 1
       ├─ GoalDelivery (steer / follow_up / replace)
       ├─ GoalRevision 2
       │    └─ TaskRun slice 2
       └─ GoalTransition / GoalObservation lineage
```

M3.8 不把 `TaskRun` 改成长生命周期对象，不扩大既有 TaskRun 状态集合，也不允许模型成为状态机、证据复用、Patch Apply 或 Draft rebase 的权威。

## 2. 已有边界与新增职责

M3.7 继续负责：

- Goal Interpreter、冻结 obligation、DAG、Controller 和 Completion Gate；
- 静态 `analyze`、`audit`、`propose_mutation` capability registry；
- 单 TaskRun 内的有限调用、无进展停止和候选哈希闭合；
- General Mutation Binder、Simulation、Closure Repair 和待审批 PatchSet；
- M3.6 Chat Public allowlist 与内部信息隔离。

M3.8 新增：

- GoalSession、GoalRevision、跨 TaskRun checkpoint 与 observation lineage；
- clarification、Patch review、stale、cancel、supersede 等长期状态；
- 显式 `steer`、`follow_up`、`replace` 消息投递；
- 安全点上的 cooperative interruption；
- crash-safe delivery claim、TaskRun continuation 与 Goal 级事件回放。

M3.8 明确不做：

- 自动 Apply、自动 Draft rebase、无限循环或后台自主 Agent；
- 跨 Project Goal、多 Agent、subagent、Hook 插件或自由工具调用；
- 运行中改写 TaskRun 冻结输入；
- 把完整 Draft/candidate、内部 Prompt、Provider、hash 或 Binder 参数放入公共事件；
- 前端组件、交互或样式开发。

## 3. 不变量

1. `GoalSession > TaskRun`，一个 Goal 可以包含多个顺序执行的 TaskRun slice。
2. 同一 Thread 同时最多一个非终态 GoalSession，也最多一个 `queued/running/cancelling` TaskRun。
3. steer 在安全点使当前 TaskRun 以 `succeeded + checkpointed` 收敛，再创建新 TaskRun；不得用 `cancelled` 表示正常转向。
4. `TaskRun.status` 保持 `queued/running/cancelling/succeeded/failed/cancelled`，waiting/stale/superseded 只属于 GoalSession。
5. GoalRevision、obligation、依赖、observation 和 transition 只追加；历史 revision 不原地修改。
6. JSONB 只承载开放诊断叶子；身份、状态、revision、队列顺序和关系使用正式列与外键。
7. Apply 仍只经过 `MutationSet → VerificationEngine → explicit approval → V1EditingService`。
8. Apply 后的新 Draft revision 是新 GoalRevision 的 `baseline`；不增加 `target_state="applied"`。
9. Draft 身份或 revision 变化统一进入 `stale`；候选和 mutation observation 失效，必须由用户显式 steer 或 replace。
10. Goal Finalizer 只在整个 Goal `completed` 时调用一次；非终态切片使用确定性公开模板。
11. `agent_runtime` 保持无数据库、SQLAlchemy、FastAPI 和 Worker 依赖；持久化编排属于 application/worker。
12. General Mutation Suggest/Patch 始终保持 `no_auto_apply=true`。

## 4. GoalSession 状态机

### 4.1 状态

```text
interpreting
running
waiting_clarification
waiting_patch_review
stale
completed
cancelled
superseded
failed
```

终态为 `completed/cancelled/superseded/failed`。终态 GoalSession 不得恢复；后续工作创建新 GoalSession，并通过 predecessor/supersede lineage 关联。

### 4.2 合法转换

| From | To | 触发条件 |
|---|---|---|
| `interpreting` | `running` | Goal 资格通过并冻结首个 GoalRevision |
| `interpreting` | `completed` | 非 Goal 请求走既有 single-turn fallback |
| `interpreting` | `waiting_clarification` | 多步骤意图成立但缺少安全执行所需信息 |
| `interpreting` | `cancelled/failed` | 用户取消或不可恢复失败 |
| `running` | `running` | steer 产生新 GoalRevision 和新 TaskRun slice |
| `running` | `waiting_clarification` | Controller 无法在权威边界内安全继续 |
| `running` | `waiting_patch_review` | 形成待审批 PatchSet |
| `running` | `stale` | Current Draft 身份或 revision 已变化 |
| `running` | `completed/cancelled/superseded/failed` | 完成、取消、replace 或不可恢复失败 |
| `waiting_clarification` | `interpreting/running` | 显式 steer 补足或修改 Goal |
| `waiting_clarification` | `stale/cancelled/superseded` | Draft 变化、取消或 replace |
| `waiting_patch_review` | `running` | Patch Apply 后绑定新 baseline 并排队 post-apply audit |
| `waiting_patch_review` | `waiting_clarification` | Patch Reject，等待换方案 |
| `waiting_patch_review` | `stale/cancelled/superseded` | revision 冲突、取消或 replace |
| `stale` | `interpreting/running` | 用户显式 steer，在新 baseline 上重建 |
| `stale` | `cancelled/superseded` | 取消或 replace |

未列出的转换必须失败关闭，并返回稳定应用错误码。

## 5. 消息投递协议

现有消息创建请求在 M3.8-02 增加：

```text
delivery_mode?: new_goal | steer | follow_up | replace
expected_goal_id?: integer
expected_goal_revision?: integer
```

规则：

- rollout=`off` 时忽略历史 GoalSession 并保持 M3.7 单次 TaskRun；请求携带任何 M3.8 delivery mode 时失败关闭。
- rollout=`shadow/active` 且没有活跃 GoalSession 时，省略模式等价于 `new_goal`；显式 `new_goal` 创建 GoalSession。
- 存在活跃 GoalSession：必须显式使用 `steer/follow_up/replace`，并携带期望 Goal ID/revision。
- steer/follow-up/replace 立即保存 user message、pending assistant message 和 delivery，但不创建第二个活跃 TaskRun。
- `steer` 和 `replace` 共享 control queue，按 `AgentMessage.sequence_no` FIFO，每个安全点消费一条。
- `follow_up` 不参与中途轮询；只有前序 Goal 为 `completed` 时才创建后继 GoalSession。
- 前序 Goal 为 cancelled/failed/superseded 时，其未消费 follow-up 转为 cancelled。
- `replace` 在安全点把旧 Goal 标记 `superseded`，取消旧 Goal 其余 delivery，再以该消息创建新 GoalSession。
- cancel 不是自由文本分类结果；Goal cancel/run cancel 进入同一权威应用服务，并优先于 queued steer/replace。
- 不让 LLM 决定 delivery mode。LLM 只解释已被用户明确标记为 steer 的语义 amendment。

M3.8-02 已实现消息投递持久化、Goal 查询/事件/SSE/cancel 和公共 DTO。M3.8-03 在 active rollout 下由 Worker 安全点轮询 queued steer，并通过应用事务消费一条。M3.8-04 补齐 clarification、Patch review、stale 和 cancellation 闭环。M3.8-05 首次使用 `casefile-chat-v18` 解释 steer amendment；M3.8-07 诊断后以 `casefile-chat-v19` 强化自包含目标摘录与 refine 重算语义，`casefile-chat-v20` 进一步冻结结构差异分类和单义务 Finalizer 输入。服务端继续验证并追加 GoalRevision；运行中的 steer/replace 共享 FIFO 单条消费，waiting steer 在解释成功后才消费，follow-up 只允许从 completed Goal 创建后继 GoalSession。M3.8-06 在运行中 control 进入 amendment/replace Provider 调用前先绑定 TaskRun/TaskAttempt claim lease，并允许新 Attempt 回收过期 claim。

## 6. 安全点与 TaskRun Slice

允许检查 interruption 的位置：

1. Goal Controller 调用前；
2. capability 完整完成并持久化 observation 后；
3. Goal Finalizer 调用前。

以下区域必须保持原子或等待自然返回：

- Provider 调用；
- General Mutation Planner/Binder；
- Simulation、Closure Repair 和 Verification；
- Patch Apply/Undo/Redo 数据库事务；
- TaskRun terminal finalization。

steer 命中安全点后的原子收敛顺序：

```text
persist checkpoint/observations
  → complete current assistant slice with deterministic public message
  → mark current TaskRun succeeded + checkpointed result
  → consume exactly one delivery
  → create GoalRevision N+1
  → create exactly one queued TaskRun slice N+1
  → commit
```

若事务失败，delivery 保持 queued/可回收 claimed，不得出现已消费消息但没有 continuation TaskRun 的状态。

M3.8-03 的落地边界：

- `GoalExecutionRunner` 可在上述三个位置返回 `goal-execution-checkpoint.v1`，并只接受 obligations hash 完全匹配的 Checkpoint 恢复；Checkpoint 保存权威 Observation、可选 Completion proof 与 mutation proof，不携带数据库对象。
- 应用层先冻结首个 GoalRevision/Obligation DAG 并绑定 initial TaskRun；安全点事务把旧 TaskRun/Attempt 标记成功、绑定标记 checkpointed、保存 Checkpoint hash、完成旧 assistant 确定性公开模板、消费一条 steer、追加 carry-forward Revision，并创建唯一 queued continuation TaskRun。
- read-only capability Observation 在 Checkpoint 事务中追加到关系表。M3.8-04 在完整 General Mutation 切片自然完成并创建 PatchSet 后，才以该 PatchSet identity 追加 mutation Observation；安全点仍不得伪造 mutation identity。
- M3.8-05 的 steer 在每个安全点只读取并消费 FIFO 队首；replace 原子收敛旧 slice、把旧 Goal 标为 superseded 并创建带 predecessor lineage 的后继 Goal。

## 6.1 M3.8-04 HITL 与 Patch 审阅闭环

- Interpreter 对多步骤 Goal 返回 typed ambiguity/missing info 时，首个 GoalRevision 仍被持久化，当前 TaskRun 使用确定性澄清回复成功收敛，Goal 进入 `waiting_clarification`；下一条显式 steer 创建新 GoalRevision 和唯一 queued continuation。
- 形成 PatchSet 的 Goal 不进入 completed，而是以 `active_patch_set_id` 进入 `waiting_patch_review`；Patch 必须继续经过显式 Apply API，不存在自动 Apply 路径。
- Reject 使用空选择完成审阅，PatchSet/operation 进入 rejected，Goal 清除 active patch 并进入 `waiting_clarification`。
- Apply 事务在既有 MutationSet、Simulation、Verification 和 V1EditingService 写入链之后，把新 Draft revision/hash 绑定为 `post_apply` GoalRevision baseline，并只创建一个 `verification_trigger=post_apply` 的审计 TaskRun。
- Apply 前发现 Draft ID/revision 不匹配时，先持久化 PatchSet/Goal `stale` 再返回冲突；旧 PatchSet 后续因非 pending 状态不能再次应用。
- Goal cancel 与 Goal 关联 Run cancel 共享同一个 aggregate cancellation authority，同时取消全部非终态 slice 和 queued/claimed delivery。

## 6.2 M3.8-06 Delivery Claim 与崩溃恢复

- `GoalExecutionRunner` 命中安全点后，Worker 在解释 steer amendment 或 replacement 之前，以短事务锁定 TaskRun、当前 TaskAttempt、GoalSession 和 FIFO 队首，并把 delivery 从 `queued` 推进为 `claimed`。
- `claimed_by` 使用 TaskRun/TaskAttempt fencing identity，`lease_expires_at` 与当前 TaskRun lease 对齐；身份不进入公共 DTO、事件或错误详情。
- FIFO 查询同时考虑 `queued/claimed`。未过期的队首 claim 阻止后续 control 越序；同一 Attempt 重入为幂等读取；TaskRun lease 过期并由新 Attempt 接管后，过期 claim 可直接改绑，不经过可竞争的 queued 中间态。
- steer/replace 的原子收敛事务必须验证 delivery 仍由当前 Attempt 持有；旧 Attempt、错误 delivery ID、错误 mode 或被回收的 claim 全部以 `agent_goal_delivery_conflict` 失败关闭。
- continuation 事务回滚时 delivery 保持 `claimed`、旧 TaskRun 保持 running，不会出现已消费 delivery 但缺失新 TaskRun；当前 Attempt 可重试，崩溃时由下一 Attempt 在租约过期后恢复。
- Goal/Run cancel 仍可直接把 queued 或 claimed delivery 收敛为 cancelled；终态 delivery 不可恢复或更新。

## 7. Goal Amendment 与 Observation 复用

M3.8-05 新增 versioned `GoalAmendment` 严格输出，允许：

```text
refine
add_constraint
add_obligation
remove_obligation
```

`replace` 不属于模型 amendment，由显式 delivery mode 创建新 GoalSession。删除 obligation 只有在新用户消息明确放弃该义务且来源摘录可验证时才允许。

服务器负责：

- 分配 session 内不复用的稳定 obligation key；
- 重建有序 obligation 集合和规范化依赖 DAG；
- 校验来源摘录、预算、capability/target compatibility；
- 计算 obligations/state hash；
- 决定 observation 是否可复用。

跨 TaskRun observation 仅在以下身份全部匹配时复用：

```text
Goal revision / obligations hash
Draft ID / revision / canonical hash
runtime / policy / capability registry version
action / input / upstream / output hash
target state
candidate hash or PatchSet identity (when applicable)
```

旧 revision 上未被新 revision 显式重新绑定的 observation 不计入 Completion Gate。Mutation observation 在任何 Draft mismatch 后一律失效。

M3.8-05 的落地边界：

- `casefile-chat-v18` 在 v17 全量冻结内容上新增独立 `goal_amendment` 严格组件；`casefile-chat-v19` 冻结修复后的自包含义务摘录与 refine 重算规则；`casefile-chat-v20` 冻结 Amendment 结构分类与单义务 Finalizer 输入。只有 bounded Goal 为 shadow/active 且 GoalSession rollout 为 active 时选用当前 M3.8 包，M3.7 默认路径仍使用不可变 v17。
- 模型只返回 typed amendment 草案；服务器验证 amendment kind、逐字来源摘录、稳定 obligation key、DAG、预算及 capability/target compatibility 后才冻结 revision。
- `goal-policy-v6` 对模型偶发的非逐字初始义务摘录保守回退为完整作者消息；明确分析/审计/修改请求补齐缺失义务，但初始只读/禁止修改语义会确定性移除模型臆造的 mutation obligation，且不会因否定句中的“修改”字样重新补回。显式作者确认门控的修改目标规范为 `analysis → audit → mutation` 可达顺序，显式 replace 视为自包含目标。未解析指代确定性进入 clarification，明确无修改澄清移除 mutation/candidate 义务，“放弃 X、保留 Y”按现有义务摘录确定性移除 X。显式禁止/只读消息规范为 `add_constraint` 并保持既有义务身份，明确收窄范围则无论模型投影为 remove/refine 都规范为保持形状、重绑定受影响义务的 `refine`，防止 Observation 错误复用；Goal Finalizer 公共语言失败以安全作者文案失败关闭，不再把已完成 Goal 留在 running。
- Controller 对已经完成的 obligation 重复发起 capability 时，服务器改选首个 DAG-ready 未完成义务；全部义务已满足后直接执行确定性 Completion Gate，不再为 `finish` 多调用一次 Controller。
- TaskRun 的 fenced 失败事务必须同时收敛当前 GoalSession、active slice、残留 running capability step 与 queued/claimed control；已终态或旧 revision 的 Goal 不被失败回填改写。Interactive executor 保留持久化任务失败及 Binder reason 的完整审计，不得将真实能力拒绝误报为 `interactive_goal_task_missing`，也不得把失败视为通过。定点 Pro 重跑仅是诊断证据，不拼接旧正式报告；正式资格仍需要新 clean revision 的完整 24×3。
- Observation 复用同时校验 Goal/revision obligations、Draft revision/hash、runtime/policy/capability registry、obligation capability/target/instruction，以及 checkpoint 的 action/input/upstream/output/candidate identity；不匹配项不复制到新 revision。
- follow-up 只从 completed Goal 创建新 Goal；replace 把旧 Goal 标为 superseded，并以 `predecessor_goal_session_id` 保存后继 lineage。

## 8. 会话级预算

M3.7 的每 TaskRun 预算保持不变。M3.8 额外冻结：

```text
max_goal_revisions = 8
max_task_run_slices = 12
max_consumed_steer_or_replace = 6
delivery_mode = one-at-a-time FIFO
```

达到任一上限后，GoalSession 进入 `waiting_clarification`，公开原因表示“本轮协作已达到上限，请开始新目标”；不得通过自动创建 TaskRun 绕过预算。

## 9. 稳定错误码

M3.8 应用层使用以下稳定错误码；公开层只返回安全中文说明和必要的公开并发信息：

| 错误码 | HTTP | 含义 |
|---|---:|---|
| `agent_goal_not_found` | 404 | Goal 不存在或不属于当前所有者/Project |
| `agent_goal_delivery_mode_required` | 409 | Thread 有活跃 Goal，但请求未明确投递模式 |
| `agent_goal_state_conflict` | 409 | 当前 Goal 状态不接受该动作 |
| `agent_goal_revision_conflict` | 409 | expected Goal revision 已过期 |
| `agent_goal_delivery_conflict` | 409 | delivery 已被消费、取消或重复提交 |
| `agent_goal_stale` | 409 | Draft 身份/revision 与 Goal baseline 不一致 |
| `agent_goal_budget_exhausted` | 409 | 会话级 revision/slice/steer 上限已耗尽 |
| `agent_goal_transition_invalid` | 409 | 请求的状态转换不在冻结矩阵中 |
| `agent_goal_amendment_invalid` | 422 | amendment 来源、DAG 或 obligation 规则非法 |

内部错误类、hash、Prompt、Provider、模型原文和 Binder 细节不得进入公共错误详情。

## 12. Rollout 与回滚

新增环境变量：

```text
CASEFILE_CHAT_GOAL_SESSION_ROLLOUT=off | shadow | active
```

- `off`：默认值；维持 M3.7 行为，不创建或消费 M3.8 delivery。
- `shadow`：为新 Goal 写入 session/revision/checkpoint 镜像并比较状态机结果，但运行中消息仍保持既有 busy 拒绝，不创建跨 TaskRun continuation。
- `active`：开放显式 steer/follow-up/replace 和跨 TaskRun continuation。
- `active` 要求 M3.7 `CASEFILE_CHAT_GOAL_ROLLOUT=active`，无效组合必须在配置加载时失败关闭。
- rollout mode、runtime version、policy version 和 budget 必须冻结进 GoalSession/TaskRun 审计输入。
- 回滚到 `off` 后，已有 GoalSession 仍可读取和取消，但不得自动创建新 continuation TaskRun。
- `casefile-chat-v17`、已运行的 v18 与 v19 保持不可变；M3.8 Amendment 使用 `casefile-chat-v20`，仅在 GoalSession rollout 开启时选择。

## 13. 验证边界

每个实现阶段必须至少覆盖主路径、非法转换、并发、归属、取消和公开隔离。正式 M3.8 资格只在最终 clean revision 上运行一次，冻结 24 Tasks × 3 Trials、Prompt/runtime/policy/capability 版本、Suite 指纹、隔离 `_test` 数据库和精确兼容 Pro 模型。

M3.8-07 才运行正式资格 Benchmark：必须在最终 clean revision 上冻结并完整执行 24 Tasks × 3 Trials，不复用 00–06 的定向测试作为资格证据。

M3.8-07 v2 使用严格私有 Holdout loader、真实 HTTP → Worker → PostgreSQL → continuation/Patch Review executor，以及 fail-closed qualification 编排。内部 `GoalSafePointObserver` 仅是默认关闭的 Worker 组合端口，用同步 barrier 在既有三类 safe point 通过公共消息 API 注入，禁止依赖 wall-clock sleep。v2 loader 还要求 initial 与 accepted successor 消息确实能进入生产 Goal candidate 路径，并对 delivery、Amendment、Observation invalidation、PatchOperation、transition 与 final state 使用 typed oracle 逐项评分；24 题必须覆盖 8 family 各 3 题、多消息 FIFO、提前 follow-up 拒绝、add/remove obligation、create/update/delete、clarification/Patch/stale/cancel 和至少三个 fixture。公开 Fake dev suite 与 PostgreSQL 回归只验证 harness；正式运行继续绑定现有私有 package、独立 reviewer attestation 和 descriptor fingerprints，失败后不得改题或选择性重跑。在完整私有运行完成且报告 `qualified=true` 前，本 ADR 不把 M3.8-07 标记为完成，默认 rollout 继续为 `off`。

Mutation capability 后命中 steer 时，当前 slice 先以确定性待审消息原子物化 PatchSet 与带 PatchSet identity 的 mutation Observation，并进入 `waiting_patch_review`；delivery 保持 FIFO 待处理。作者 Apply 后创建的 post-apply slice 在任何新 capability 前消费该 steer。这样既不伪造 mutation identity，也不会跨过“下一安全点”继续启动其他 capability；replace 仍保持原有控制语义，不走这条 steer 延迟路径。

任何自动 Apply、unsafe/stale Apply、错误 observation 复用、队列乱序、重复 TaskRun、跨归属串联、内部泄漏、模型身份缺失或证据完整性失败，都必须保持 `qualified=false`。
