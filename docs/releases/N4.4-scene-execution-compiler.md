# N4.4 Scene Execution Compiler

N4.4 将 N4.3 已规范化的 `compiler.novel-plan.v1` 与匹配 NarrativeIR 冻结为 `compiler.scene-compiler-input.v1`，由未来模型只填充 Scene 内来源支持的结构化 Beat，再由服务器规范化为不含正文的 `compiler.scene-plan.v1`。本阶段回答“故事如何按场景发生”，不重新规划主线，不读取 Planner Prompt/repair/benchmark 私有实现，也不承担 N4.5 的文风、对白或小说正文生成。

`Narrative Execution Benchmark v1` 最初只落地离线审计基座；当前 Runner 已升级为复用 v2 Shadow Scene Fill runtime，可从冻结审计输入确定性生成 v2 Input/ModelView，并运行 Fake regression、v2 Safety 与精确 Pro 24×3 live capability。既有纯确定性展开继续只作为 reference/baseline helper，不代表 N4.4 模型能力；首轮 live baseline 只用于观察，仍不预设晋级阈值。

## 契约命名与阶段边界

N4.2 已冻结 `NarrativeIR` 为 CaseFile Snapshot 的无损语义投影，因此 N4.4 不复用或重定义该名称。N4.4 输出使用 N4.0 已预留的 `scene_plan` Artifact kind，公开类型为 `ScenePlanIR`：

```text
CaseFile Snapshot
  → NarrativeIR          (N4.2，无损事实 IR)
  → NovelPlanIR          (N4.3，故事规划)
  → ScenePlanIR          (N4.4，执行计划)
  → prose/draft renderer (N4.5，正文)
```

Scene Compiler 消费完整、可独立序列化的 `NovelPlanIR + NarrativeIR` 冻结 Bundle，不 import Story Planner、Provider、Prompt、repair 或 benchmark 代码。模型 Candidate 不拥有 Chapter/Scene 身份、顺序、目的、POV、依赖、稳定 ID、哈希、索引或来源证明。现有 `CompileArtifact + AgentStepRun + TaskRun` 分别是产物、组件审计与执行终态的唯一权威，不额外引入重复的通用 `CompilationResult[T]`。

## ScenePlanIR v1

`ScenePlanCandidate` 只按既有 Scene 输出有序 Beat directive、kind、participant/location/time/basis refs 与 Event/Exposure/Resolution 动作。服务器校验所有引用均存在且属于该 Scene 的来源白名单，完整覆盖计划动作后，`ScenePlanIR` 保留 NovelPlan 身份与顺序并确定性派生：

- `beat_{scene_id}_{ordinal}` Beat ID 与内容寻址的稳定 Edge ID；
- Chapter → Scene、Scene → Beat、Scene prerequisite 的显式图边；
- 每个 Scene 的 objective、POV、参与者、地点、故事时间与来源证明；
- 每个 Scene 前后的读者 Exposure 状态、本场允许揭露与未来禁止揭露 key；
- Event、Exposure、Resolution 与无显式动作 Scene 的最小 transition Beat；
- chapter/scene/beat、dependency、Exposure、Resolution 派生索引与计数。

同一规范 NovelPlan 必须产生完全相同的 JSON 与 RFC 8785 SHA-256。Beat directive 是供后续 Renderer 消费和调试的结构化执行指令，不是小说正文。

## Graph 与 Linter

`NarrativeExecutionGraph` 在领域层内部封装 `networkx.MultiDiGraph`，公开契约只保存普通节点 ID 与 typed edge。当前提供 ancestors、descendants、affected nodes 与 dependency cycle 查询；NetworkX 类型不会进入 Pydantic/JSON Schema。

确定性 linter 复验 Input/Candidate 双哈希、NovelPlan 索引与依赖 DAG、Scene/Beat 覆盖、引用接地、揭露、时间、Resolution 和 provenance；规范化后生成语义签名，忽略 directive 措辞但绑定全部结构语义。Benchmark 直接复用 Shadow runtime 与 Provider adapter，但不改变 Worker 默认激活状态。

## Benchmark v1

Suite 冻结 8 个能力族与 basic/decoy/dense 三类变体，共 24 Task：Scene decomposition、Event grounding、Reveal control、Temporal grounding、Dependency transfer、Resolution execution、Scene grounding 与 Provenance coverage。每题含完整冻结输入、known-good Reference 与可审计 input evidence paths；每个能力族另有一个结构不同但合法的 Alternative，grader 不做 Reference JSON 精确匹配。

G0 检查 v2 输入绑定与 SemanticFill 契约，G1 通过权威 State Engine 完整重放，G2 按 Outcome coverage 评分，G3 仍只冻结五维 Writer executability rubric，G4 生成忽略模型措辞的结构语义签名。Capability live runtime、Regression 替代表达与 Safety mutations 分开报告；正式 Capability 精确冻结 Provider、Pro model、Prompt/Schema/runtime 指纹与每题三次 Trial，并支持 checkpoint/resume。首轮完整 baseline 完成后报告 `baseline_observed`，但在前瞻门槛尚未冻结前始终 `qualified=false`。

## 明确延期

- Character Knowledge、location/resource state、setup/payoff 与 semantic causality 不能从当前 NovelPlan 的 ID/ref-only 契约可靠推断；本版不编造这些状态。后续必须先增加来源支持的 typed obligation/input projection，再扩展 State Engine。
- 本版用确定性规则与 NetworkX 完成结构执行和验证，不引入 `z3-solver`。只有 Benchmark 证明存在大量局部规则无法处理的联合可满足性问题，或需要自动搜索合法 Scene 排列时，才评估独立 Solver backend。
- N4.4 不写正文，不评估文学性，不增加 Writer/Editor/Rewrite Agent。

## ScenePlanIR v2 影子链路

在 v1 确定性基线和独立 Benchmark 之上，N4.4 新增未默认激活的
`compiler.scene-compiler.shadow.v1`：完整审计输入绑定 NovelPlan、NarrativeIR、Exposure
与 Profile，Provider 只接收章内最多八场的最小 ModelView。模型只填写 goal、conflict、
outcome 与结构化 Beat；服务端 State Engine 重新分配 ID、重建 Exposure、应用来源支持的
Knowledge/Location 增量，并规范化 causal edge 与 setup/payoff。

影子链路产出 `compiler.scene-plan.v2`，历史 `compiler.scene-plan.v1` 继续可读、可重放。
Application Service 默认仍创建现有 Constraint-First TaskRun；只有内部显式
`scene_compiler_shadow` 运行会调用 Scene Fill。正式默认切换必须等待独立 Benchmark
完成资格校准和晋级，不以本次组件测试代替能力证据。

## v2.2 引用闭包修复与复评边界

首轮 `deepseek-v4-pro` 24×3 baseline 在 Runner v2.1 下为 18/72；42/54 失败是
`compiler_scene_fill_reference_invalid`，且 42 次全部发生在第二 batch。根因核对发现
Decoy/Dense 第二 batch 的 `state_seed` 暴露嵌套 knowledge/event 引用，但旧 ModelView
未把这些引用纳入 `object_catalog`，导致 Provider 可见语言与 Validator 白名单不闭合。

projection v2 在不改变 Suite、Prompt、SemanticFill Schema 或 Validator 严格度的前提下，
先选择与 Scene 相关的状态行，再把其中全部嵌套 ObjectRef 加入同批对象目录；无法从冻结
NarrativeIR 解析的可见引用在 Provider 调用前失败关闭。Runner v2.2/report v3 同时增加
结构化失败 path/ref/allowlist hash、失败 batch ordinal，以及仅在显式启用时保留失败 parsed
proposal 的诊断策略。

三题 Pro 诊断为 1/3、infra=0、`reference_invalid=0`：Basic 通过，Decoy 为本地 Beat
dependency 越界，Dense 为 Scene basis provenance 越权。它只证明原引用闭包故障已消失，
不是 Capability 晋级证据。完整 v2.2 24×3 在提交 `0d3afd5` 上得到 26/72、pass@3
16/24、all-three 3/24、infra 2、`reference_invalid=0`；主失败转为 provenance 31 次。
结果仍为 `baseline_observed/qualified=false`。Basic 单 batch、Decoy/Dense 双 batch 的 Suite
混杂必须在后续独立 Suite 版本中处理；详见
[`N4.4-scene-plan-v2.2-formal-report.md`](N4.4-scene-plan-v2.2-formal-report.md)。

## ModelView v3 与 Prompt v2 诊断

projection v3 把 Validator 既有 Scene/obligation basis 并集显式投影为
`beat_basis_allowlist`，但 projection-only 正式运行在用户要求下于 48/72 停止；partial
样本中的 provenance 仍为 18，与 v2.2 对齐子集相同，不能视为有效修复。随后只升级 Prompt
为 `scene-compiler-semantic-fill-v2`，明确目录存在性与顶层 Beat provenance 的两层权限。

三个 provenance 高频任务×3 的 Pro 诊断为 6/9、infra=0、provenance=0；剩余失败转为
knowledge-state 2 次和 obligation coverage 1 次。该诊断不替代完整 24×3，资格仍为
`baseline_observed/qualified=false`。下一轮若继续，应独立解决跨 batch 只传状态哈希、不传
typed knowledge/open-setup 状态的问题；详见
[`N4.4-scene-plan-modelview-v3-prompt-v2-diagnostic.md`](N4.4-scene-plan-modelview-v3-prompt-v2-diagnostic.md)。

失败降为 0；新出现的两次 obligation kind mismatch 随后通过只强化类型对齐的 Prompt v3
定向复评收敛为 3/3。两轮均 infra=0，但都不是完整 24×3，且没有 clean revision 正式证据，
资格仍为 `uncalibrated/qualified=false`。详见
[`N4.4-scene-plan-typed-state-prompt-v3-diagnostic.md`](N4.4-scene-plan-typed-state-prompt-v3-diagnostic.md)。

## Prompt v5 局部修复与用户授权晋级

按用户明确指令，不重跑完整 24×3。Prompt v5 只补充 `depends_on` 的 Scene-local 作用域：
仅允许引用当前 Scene 严格更早的 Beat local key，禁止借用同 batch 其他 Scene 的 key。
聚焦测试 35/35、Fake Capability/Regression/Safety 24/24、8/8、11/11；clean revision
`dcb8faabcef47570473ac721e8c675dd25e8ccae` 上对唯一失败 Task
`scene_decomposition__decoy` 的全新 Pro 局部验证为 3/3、infra=0、所有失败族为 0。

用户授权将 v4 完整正式基线 71/72 与 v5 唯一失败 Task 3/3 局部复验视为本阶段晋级，产品
决策记为 `user_authorized_promoted`。局部机器报告仍诚实保持
`uncalibrated/qualified=false`，不伪装成完整 qualification；详见
[`N4.4-scene-plan-prompt-v5-targeted-promotion.md`](N4.4-scene-plan-prompt-v5-targeted-promotion.md)。
