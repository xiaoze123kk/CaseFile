# N4.4 ModelView v3 与 Prompt v2 诊断报告

## 结论

ModelView projection v3 单独增加 `beat_basis_allowlist` 后，并未稳定降低 provenance
失败；用户在正式运行 48/72 时要求停止，checkpoint 保持 `partial=true`，没有生成正式
report，也不作资格或完整通过率解释。

随后保持 projection v3、Suite、Validator、模型与预算不变，只把 Scene Fill Prompt 升级
为 v2，明确区分对象目录存在性和顶层 Beat provenance 权限。三个高风险任务各 3 次的
`deepseek-v4-pro` 诊断中，provenance 从所选任务此前的主要失败降为 0，最终为 6/9、
infra=0。剩余失败是 2 次 knowledge-state 冲突和 1 次 obligation coverage，不再属于
本轮 allowlist 问题。

本轮不恢复 48/72 partial checkpoint，不启动新的完整 24×3，资格继续保持
`baseline_observed / qualified=false`。

## Projection-only partial 证据

projection v3 只在每个 Provider-facing Scene 上增加稳定排序的
`beat_basis_allowlist`，其值严格等于现有 Validator 使用的
`scene.basis_refs ∪ obligations[*].basis_refs`。`object_catalog` 没有被加入白名单，
Validator 仍从权威 Scene/obligation 字段派生允许集合。

正式 24×3 运行按用户要求在 48 个 trial 后终止：

- checkpoint：`partial=true`
- 完成：48/72
- 通过：22/48
- provenance：18
- setup unpaid：3
- location subject：2
- obligation coverage：1
- actor scope：1
- setup duplicate：1
- infrastructure：0

与 v2.2 正式报告中相同 48 个 trial ID 对齐时，v2.2 为 19/48，provenance 同样为 18。
这不是随机配对实验，因此不能把 +3 解释为因果增益；可以确认的是 projection-only 没有
降低核心 provenance 计数。18 次首个越界引用仍全部为 `info_restart_log`，说明仅增加字段
不足以让模型理解“目录可见不等于 provenance 可用”。

## Prompt-only 小规模诊断

Prompt v2 只新增一条权限分层规则：

- `object_catalog` 只证明引用存在，可用于 actor、target 或嵌套状态引用；
- 顶层 `Beat.basis_refs` 必须逐项来自所属 Scene 的 `beat_basis_allowlist`；
- 出现在 `object_catalog` 或 `state_seed` 中但不在 allowlist 的引用，不得写入顶层 basis。

诊断选择 projection-only partial 中 provenance 高频的三个任务，各运行 3 次：

| Task | 结果 | 失败 |
|---|---:|---|
| `scene_decomposition__decoy` | 0/3 | knowledge-state 2、obligation coverage 1 |
| `reveal_control__decoy` | 3/3 | 无 |
| `temporal_grounding__dense` | 3/3 | 无 |

汇总：

- 通过：6/9
- provenance：0
- reference invalid：0
- infrastructure：0
- 指纹：`1c1250936ee6900207a48a822448b57c0c4c4a9167e7777d4980670635de6f64`

该结果支持 Prompt v2 作为 allowlist 接口修复，但样本仅 9 个 trial，不能替代 24×3，
也不能晋级。

## 下一层根因

两个 `compiler_scene_known_fact_cannot_be_false_belief` 都发生在第二 batch。模型在当前
batch 根据冻结 `state_seed` 对 `claim_manual_trigger` 发出 `misbelieve`，但 State Engine
完整重放时，前一 batch 的模型输出可能已经把同一对象变为 known fact。后一 batch 只收到
不透明 `inbound_state_hash`，看不到前一批实际知识状态或允许的 operation，因此无法稳定
满足动态前置条件。

下一轮如继续，应单独设计 typed inbound state 实验：

1. 每批 Scene Fill 通过后增量应用权威 State Engine prefix；
2. 下一批接收结构化、最小化的 knowledge/open-setup 状态，而不只是哈希；
3. 按 subject/object 显式投影允许的 knowledge operation；
4. setup/payoff 使用服务端分配的 typed key，不允许模型自由发明；
5. 冻结 Prompt v2 和 projection v3，只改变 inbound state contract。

不要用 Validator 放宽、静默 canonicalizer 或把所有目录对象加入 provenance 白名单替代该
状态闭环。
