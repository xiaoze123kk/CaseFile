# N4.4 ScenePlan Benchmark 成功率优化复盘报告

## 一、执行摘要

本轮 N4.4 ScenePlan Benchmark 优化的核心结果，是把完整 24 Task×3
`deepseek-v4-pro` 正式成功率从 v2.2 的 26/72（36.11%）提升到 Prompt v4 的
71/72（98.61%）：

- 正式通过 trial：26 → 71，增加 45 次；
- 正式成功率：36.11% → 98.61%，提高 62.50 个百分点；
- pass@3：16/24 → 24/24；
- 三次全过：3/24 → 23/24；
- Basic：18/24 → 24/24；
- Decoy：2/24 → 23/24；
- Dense：6/24 → 24/24；
- 基础设施失败：2 → 0。

这不是一次“换模型”或“放宽 Validator”带来的提升。正式 suite、精确 Pro 模型、三次 trial、
核心 Schema、Validator、State Engine 与 G0–G4 评分边界始终保持冻结。成功率提升来自一系列
按失败族推进的单变量闭环：先补齐 Provider 可见输入，再明确引用权限，随后把跨 batch 动态
状态变成 typed contract，最后逐项收口 obligation、setup/payoff 与 Beat dependency 的局部
作用域。

Prompt v4 完整正式复评只剩 1 次跨 Scene Beat local key 错误。Prompt v5 仅补充
`depends_on` 的 Scene-local 规则，并对唯一失败 Task 运行 3 次 Pro 局部验证，结果 3/3。
按用户明确授权，产品决策记录为 `user_authorized_promoted`。机器 qualification 仍保留
`qualified=false`，因为 Prompt v5 没有重新运行完整 72 次；局部报告没有被伪装或拼接成新的
全量正式报告。

## 二、报告范围与证据口径

本报告区分三类证据：

1. **完整正式结果**：24 Task×3、精确 `deepseek-v4-pro`、完整 selection、全新
   checkpoint，可用于比较整体成功率。
2. **局部 Pro 诊断**：只选择目标失败 Task，用于验证单一根因是否闭合，不替代完整正式
   结果。
3. **确定性门禁**：Fake Capability、Regression、Safety、契约、静态检查与 pytest，用于证明
   Validator/State Engine 没有被弱化，也没有引入结构或安全回归。

正式成功率的最终可比结论停在 Prompt v4 的 71/72。Prompt v5 的 3/3 是用户授权晋级所采用
的局部补充证据，不写成“新正式结果 72/72”。

## 三、完整正式指标演进

| 阶段 | Revision | 正式结果 | 成功率 | pass@3 | 三次全过 | 主要失败族 |
|---|---|---:|---:|---:|---:|---|
| v2.1 初始 Shadow baseline | `70fc362` | 18/72 | 25.00% | 8/24 | 4/24 | reference invalid 42、setup 6、provenance 5 |
| v2.2 引用闭包 | `0d3afd5` | 26/72 | 36.11% | 16/24 | 3/24 | provenance 31、setup 8、dependency/payoff |
| Typed State + Prompt v3 | `2dd6a39` | 63/72 | 87.50% | 24/24 | 17/24 | setup unpaid 9 |
| Setup/Payoff Prompt v4 | `667cdc2` | 71/72 | 98.61% | 24/24 | 23/24 | dependency invalid 1 |

从最早 v2.1 Shadow baseline 到 Prompt v4，完整正式结果由 18/72 提升到 71/72，增加
53 个通过 trial、提高 73.61 个百分点。以本次主要优化起点 v2.2 计算，则增加 45 个通过
trial、提高 62.50 个百分点。

### Variant 改善

| Variant | v2.2 | Prompt v3 | Prompt v4 | v2.2 → v4 |
|---|---:|---:|---:|---:|
| Basic | 18/24 | 22/24 | 24/24 | +6 |
| Decoy | 2/24 | 22/24 | 23/24 | +21 |
| Dense | 6/24 | 19/24 | 24/24 | +18 |

最大增益来自 Decoy 与 Dense。v2.2 时它们均为双 batch，Provider 会遇到对象目录闭包、动态
知识状态、开放 setup 与更复杂 obligation 组合；后续优化正好逐层解决了这些跨 batch 信息与
权限问题。因此，这一提升主要说明执行接口变得可理解、可遵守，而不是简单说明模型在复杂题上
“推理能力突然增强”。

## 四、优化历程

### 1. v2.2：先修输入闭包，让模型看到合法引用

v2.1 的主失败是 `compiler_scene_fill_reference_invalid=42`，且全部集中在第二 batch。根因是
状态种子把嵌套知识/事件引用暴露给 Provider，却没有把相同对象补进 `object_catalog`。

projection v2 补齐可见状态引用的目录闭包，并在缺少 NarrativeIR 对象时于 Provider 调用前
失败关闭。完整复评中 reference invalid 从 42 降为 0，成功率从 18/72 提升到 26/72。

这一轮也揭示了一个重要现象：修掉 42 次 reference failure 后，只增加 8 个通过 trial。
原因不是修复无效，而是旧错误曾遮蔽后续门禁；输入闭包修好后，31 次 provenance 越权成为
新的主失败族。

### 2. Projection v3：只增加 allowlist 字段并不够

ModelView projection v3 把 Validator 已有的 Scene/obligation basis 并集显式投影为
`beat_basis_allowlist`。但 projection-only 运行在 48/72 时仍有 18 次 provenance 失败；与
v2.2 的相同 48 个 trial 对齐时，provenance 计数同样为 18。

这是本次优化中最有价值的负结果：结构化字段“存在”不等于模型理解其权限语义。
`object_catalog` 和 `beat_basis_allowlist` 同时出现时，如果 Prompt 没有解释二者的权限层级，
模型仍会把“可见对象”误当成“可作为顶层 provenance 的对象”。

### 3. Prompt v2：把存在性与 provenance 权限分层

Prompt v2 明确：

- `object_catalog` 只证明 ObjectRef 存在，可用于 actor、target 或嵌套状态引用；
- 顶层 `Beat.basis_refs` 必须逐项来自当前 Scene 的 `beat_basis_allowlist`；
- 目录可见但不在 allowlist 的对象，不能作为顶层 Beat provenance。

三个 provenance 高频 Task×3 的局部 Pro 诊断为 6/9，provenance 从主要失败降为 0，
infra=0。剩余失败转为 knowledge-state 2 次和 obligation coverage 1 次。

这证明有效变量不是“再加一个字段”，而是把服务器权限模型翻译成模型可执行的明确规则。

### 4. Typed inbound state：把跨 batch 隐状态变成契约

Prompt v2 后的 knowledge-state 失败发生在第二 batch。前一 batch 已经改变角色知识，但后一
batch 只收到不透明 `inbound_state_hash`，看不到当前 known fact，也不知道允许执行
`learn/believe/misbelieve/correct` 中的哪些操作。

新建 `compiler.scene-compiler-inbound-state.v1` 后，下一批显式收到：

- 当前角色知识；
- known fact 的操作白名单；
- 开放 setup；
- 全部已用 setup key；
- 与完整内部状态共同绑定的 state/input hash。

同一组三 Task×3 的局部诊断由 6/9 提升到 7/9，knowledge-state 失败从 2 降为 0，
`scene_decomposition__decoy` 从 0/3 提升到 3/3。剩余两次失败收敛为 obligation kind
mismatch。

这一步是整体跃升的关键基础：模型不再需要从历史文本或哈希猜测动态状态，而是消费由服务器
投影、Schema 校验、hash 绑定的最小 typed state。

### 5. Prompt v3：锁定 obligation.kind 与 Beat.kind

Prompt v3 只增加类型对齐规则：

- 完成某个 obligation 的 `Beat.kind` 必须完全一致；
- 同一个 Beat 不得合并不同 kind 的 obligation；
- event、exposure、resolution obligation 必须拆成对应类型的独立 Beat。

唯一失败 Task 的局部 Pro 复验为 3/3，kind mismatch 清零。随后在 clean revision
`2dd6a39` 上运行完整 24×3，结果从 26/72 跃升到 63/72：

- provenance、knowledge-state、obligation kind 全部清零；
- pass@3 达到 24/24；
- 基础设施失败为 0；
- 剩余 9 次失败全部收敛到 `compiler_scene_setup_unpaid`。

这次 51.39 个百分点的提升不是 Prompt v3 一条规则单独贡献，而是引用闭包、权限分层、typed
state 与类型对齐共同生效后，在完整分母上的首次集中体现。

### 6. Prompt v4：把 setup/payoff 定义成默认空、必须闭环的可选标记

完整 v3 复评显示，setup/payoff 是唯一剩余失败族。冻结输入中没有要求模型必须创造新的
setup；模型为了丰富执行结构主动创建 setup，却没有稳定兑现，最终被 State Engine 的
`compiler_scene_setup_unpaid` 正确拒绝。

Prompt v4 明确：

- `setup_keys` 与 `payoff_keys` 默认保持空数组；
- 只有同一 batch 中存在严格后续 Beat 能兑现时，才允许创建新 setup；
- 新 setup 的创建与兑现必须各出现一次，不得跨 batch 延后；
- `inbound_state.open_setups` 是当前 batch 必须逐项兑现的显式 payoff 义务；
- 无法保证闭环时，不得创建新 setup。

先对上一轮所有 7 个失败 Task 运行 21 次局部 Pro 诊断，结果 21/21。随后在 clean revision
`667cdc2` 上运行完整 24×3：

- 71/72，98.61%；
- 23/24 Task 三次全过；
- setup unpaid 9 → 0；
- Basic 24/24、Dense 24/24；
- 唯一失败变为 1 次跨 Scene Beat local dependency。

### 7. Prompt v5：收口 `depends_on` 的 Scene-local 作用域

Prompt v4 唯一失败中，`scene_4` 首个 Beat 把同 batch 上一个 `scene_3` 的
`beat_local_scene_3_event_001` 写入 `depends_on`。Validator 的语义一直是 Scene-local：
只能引用当前 Scene 中严格更早出现的 Beat local key；跨 Scene 关系由
`prerequisite_scene_ids` 和 `scene_enables_scene` 表达。

Prompt v5 只把这条既有规则说透，没有修改 Validator。聚焦测试 35/35，Fake
Capability/Regression/Safety 为 24/24、8/8、11/11；clean revision `dcb8faa` 上只运行
`scene_decomposition__decoy` ×3，结果 3/3，所有失败 taxonomy 与 infra 均为 0。

按用户明确授权，本阶段产品决策记录为 `user_authorized_promoted`。由于没有重跑完整 72 次，
Prompt v5 的机器报告仍是局部诊断，不能表述为新的完整正式 72/72。

## 五、失败族如何逐层收敛

| 阶段 | 被清零的目标失败 | 清零后暴露的下一层问题 |
|---|---|---|
| v2.2 引用闭包 | reference invalid 42 → 0 | provenance 31 |
| Prompt v2 权限分层 | 局部 provenance → 0 | knowledge-state、obligation coverage |
| Typed inbound state | 局部 knowledge-state 2 → 0 | obligation kind mismatch 2 |
| Prompt v3 类型对齐 | 局部 kind mismatch → 0 | 完整正式 setup unpaid 9 |
| Prompt v4 setup 闭环 | 完整正式 setup unpaid 9 → 0 | dependency invalid 1 |
| Prompt v5 局部作用域 | 目标 Task dependency invalid → 0 | 局部 3/3 无失败 |

这条链路说明，早期低成功率并非单一“模型能力不足”，而是多层接口契约问题叠加。每次只修
当前主失败族，旧错误消失后，下一层约束才会变得可见。若一开始同时改 Prompt、Schema、
Validator 和 State Engine，就无法判断 62.50 个百分点的增益来自哪里，也很难避免通过放宽
门禁制造虚假提升。

## 六、为什么这套方法有效

### 1. 把服务器权威翻译为模型可执行规则

Validator 已经知道什么是合法，但模型最初看不到或看不懂这些边界。优化没有把权威交给模型，
而是把权威规则以 allowlist、typed state、kind 和作用域说明投影给模型；最终接受与否仍由
服务器决定。

### 2. 动态状态必须 typed，不能只传 hash

hash 能证明一致性，不能向模型解释当前状态。跨 batch 的知识、开放 setup 与已用 key 必须
同时具备：内部权威状态、最小可见投影、Schema 校验和 hash 绑定。

### 3. 默认空比鼓励模型“丰富结构”更安全

当冻结输入没有 typed setup obligation 时，模型自发增加 setup 并不提升目标能力，只增加
闭环失败面。Prompt v4 把可选字段恢复为保守默认，同时保留 State Engine 对合法 setup/payoff
的完整支持。

### 4. 负结果同样决定方向

Projection v3 单独加 `beat_basis_allowlist` 没有稳定收益，阻止了继续堆字段或扩大白名单。
它推动下一轮把注意力从“数据有没有”转向“权限语义是否清楚”。

### 5. 诊断与正式复评分层

局部诊断先证明目标失败族闭合，再决定是否花费完整 24×3 成本。完整成功率只来自全新、完整、
revision-bound 的正式报告；Prompt v5 的例外由用户明确授权，并在机器资格之外单独记录。

## 七、确定性与安全边界

整个优化过程中保持以下原则：

- 不放宽 Scene Fill Validator；
- 不删除 State Engine 的 setup 必须兑现规则；
- 不把 catalog 对象整体加入 provenance allowlist；
- 不用静默 canonicalizer 改写失败输出；
- 不改变 24 Task suite、精确 Pro 模型或 3-trial 正式参数；
- Fake Capability/Regression/Safety 始终保持 24/24、8/8、11/11；
- 原始 report/checkpoint 保持在 Git 忽略的 `backend/var`，不进入仓库；
- `scripts/check.ps1 -SkipPostgres` 的通过不冒充完整 PostgreSQL 门禁。

因此，成功率提升代表模型输出更频繁地满足原有严格契约，而不是评分器变宽松。

## 十、最终结论

本轮优化把 ScenePlan 的主要瓶颈从“多类契约错误混杂”逐层压缩到单一、可解释、可局部修复
的作用域错误。完整正式成功率从 36.11% 提升到 98.61%，同时保持 Validator、State Engine
与 Safety 门禁不变；唯一正式失败随后在 Prompt v5 的目标 Task 上完成 3/3 局部验证。

真正可复用的经验不是某一段 Prompt 文案，而是这套过程：

> 用结构化失败证据定位主失败族；冻结其余变量；把服务器权威投影成最小 typed contract 与
> 明确权限语义；先做目标诊断，再决定是否完整复评；永远不通过放宽确定性门禁换取成功率。

这使 62.50 个百分点的提升具备可解释性、可复验性与后续可维护性，而不是一次不可归因的
模型波动。
