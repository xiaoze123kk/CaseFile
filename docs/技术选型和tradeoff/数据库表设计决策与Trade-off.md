# CaseFile 数据库表设计决策与 Trade-off

## 1. 决策结论

CaseFile 个人版数据库底座最终采用：

> **轻量对象注册表 + 规范化专用内容表 + 统一多值引用边 + 不可变完整 JSON 快照**

最终建立 28 张业务表。所有关系表使用 `BIGINT GENERATED BY DEFAULT AS IDENTITY` 自增主键；数据库内部外键统一使用 `BIGINT`。只有需要写入 CaseFile JSON 契约的核心内容对象保留稳定字符串 `casefile_objects.object_id`。

当前态以专用关系表为唯一事实源，开放叶子结构才使用 JSONB；Snapshot 和 Canon 则保存完整、不可变的 CaseFile JSON。第一版只面向个人用户，不建立 Workspace、Membership 或任何团队协作占位结构。

这不是追求“表越多越好”，而是在三类目标之间取得平衡：数据库能约束关键事实、开发者能理解领域结构、CaseFile JSON 仍能灵活演进。

## 2. 决策范围与输入

本次决策只覆盖以下底座链路：

```text
个人用户 → Project → CaseFile → 当前 Draft
                         ├─ 当前态内容与关系
                         └─ Operation → Snapshot → Canon → Audit
```

主要输入来自：

- CaseFile PRD v2.3 对 Entity、Event、Information Unit、Claim、Hypothesis、Reasoning Path、Resolution Spec、Narrative Phase、Knowledge State、Draft 和 Canon 的定义。
- 架构分析材料中对 Person、Location、Evidence、Testimony 等具体对象的字段分析。
- 产品边界：当前只服务个人用户，正式版本只能由项目所有者本人确认。
- 工程约束：PostgreSQL 18、SQLAlchemy 2、Alembic、psycopg，以及可执行的数据库级一致性测试。
- 明确的实现偏好：自增主键、时间戳迁移、大写 `V` 文件前缀，不引入 UUID 或额外 `public_id`。

认证、导入、素材、Validator、Simulation、Compiler、Export、预算、删除工作流和团队协作不属于本次定表范围。没有足够当前需求支撑的表，不因“以后可能有用”而提前创建。

## 3. 我是怎样定下这 28 张表的

### 3.1 先定产品边界，而不是先画表

第一个决定是产品只面向个人用户。因此所有权根可以稳定为：

```text
users 1 ── N projects 1 ── 1 casefiles 1 ── 1 current drafts
```

Project 只有一个不可转移的 `owner_user_id`。这一步直接排除了 Workspace、Membership、成员角色、邀请、评论、Review Task、共享项目和团队预算，也避免为了未发生的团队需求污染所有后代表。

### 3.2 再区分“当前态”和“不可变历史”

CaseFile 同时需要频繁编辑和稳定发布。如果只存一份 JSON，每次修改都会覆盖过去；如果每次小修改都复制完整文档，编辑成本又过高。因此拆成两类存储：

- 当前 Draft：使用可更新的规范化关系表，适合局部编辑、约束和查询。
- 历史版本：Snapshot 与 Canon 保存完整不可变 JSON，适合确认、哈希、复现和下游编译。

`draft_operations` 只描述增量编辑，`audit_events` 只描述责任事件；它们都不是内容事实源。

### 3.3 第一版候选曾是“注册表 + 通用 payload_jsonb”

早期底座曾考虑只建立约 10 张表：所有领域对象共用 `casefile_objects`，正文统一放在 `payload_jsonb`。它的优点是表少、迁移少、接收新对象类型快。

进一步对照 PRD 和具体对象字段后，这个方案暴露出四个问题：

1. 开发者看到一行对象无法从表结构判断它究竟有哪些可靠字段。
2. Person、Location、Evidence、Testimony 的必填字段、类型和外键很难由数据库约束。
3. Event → Location、Testimony → Speaker 等稳定关系会退化为 JSON 内字符串，跨 Draft 和跨 Project 串联更难阻止。
4. 常用字段的查询、索引、迁移和影响分析都依赖解析异构 JSON。

因此放弃“正文主要存 `payload_jsonb`”，并从 `casefile_objects` 删除该字段。

### 3.4 保留轻量对象注册表，但把正文拆进专表

完全删除对象注册表也不可取。CaseFile JSON 需要稳定字符串 ID，Claim、Information Unit、Event、Hypothesis 等不同类型之间又需要统一引用端点。因此保留 `casefile_objects`，但把职责收窄为：

- 为 10 类核心对象登记稳定 `object_id` 和 `object_type`。
- 保存对象级 revision、来源、置信度、确认状态和软删除状态。
- 为跨类型引用、Reasoning 来源和 Constraint 目标提供统一内部端点。

具体正文写入 18 张专用内容表。这样既保留跨类型统一身份，又让字段和约束在数据库中可见。

### 3.5 用“通用基类 + 具体扩展”处理相似对象

Person 与 Location 都是 Entity；Evidence 与 Testimony 都是 Information Unit。如果每种具体类型都复制名称、正文、可信度等共有字段，模型会快速漂移。因此采用两组 1:1 扩展：

```text
casefile_objects(object_type=entity)
  └─ entities
       ├─ people       仅当 entity_kind=person
       └─ locations    仅当 entity_kind=location

casefile_objects(object_type=information_unit)
  └─ information_units
       ├─ evidence_items  仅当 information_kind=evidence
       └─ testimonies     仅当 information_kind=testimony
```

数据库触发器验证注册类型、基类判别类型和扩展表一致。Organization、Object、Concept、Document、Observation、Clue 等暂时只需基类行，不为没有专属字段的类型空建一张表。

### 3.6 单值关系用外键，多值跨类型关系用统一引用边

关系没有全部塞进 JSON，也没有为每一种关系各建一张表，而是按稳定性区分：

- 稳定、单值、结构明确的关系使用专表 `BIGINT` 外键，例如 Event → Location、Evidence → Source Event、Testimony → Speaker Person。
- 多值、跨对象类型、有顺序或带扩展属性的关系使用 `casefile_refs`，例如 Event → Actors、Information Unit → Claims、Hypothesis → Claims/Required Information、Location → Adjacent Locations。

已知 `ref_kind` 由数据库触发器验证端点类型；未来 Schema 自定义引用由应用层 JSON Schema Validator 验证。这避免引用表无限增殖，同时没有放弃核心关系完整性。

### 3.7 把“推理过程”和“最终答案结构”分开

`reasoning_paths + reasoning_nodes + reasoning_edges` 回答“为什么能推出结论”；`resolution_specs + resolution_slots` 回答“项目最终必须回答什么、答案有哪些动态字段”。两者不能合并：一个项目可以存在多条竞争推理路径，但每个 Draft 只有一份当前目标问题规格。

固定 `answer_tuple` 也被放弃。不同项目不一定都回答“谁、为什么、如何、何时、何地”，因此由 Resolution Spec 定义问题，由 Slots 定义该问题真正需要的答案字段。

### 3.8 加入叙事阶段和知识状态

仅有事实和证据不足以表达互动推理内容，因为“某信息为真”不等于“某角色此刻知道它”。因此加入：

- `narrative_phases`：定义内容推进和发布阶段。
- `knowledge_states`：定义 Entity 在某 Phase 的总体认知。
- `knowledge_state_entries`：逐条记录该 Entity 对 Information Unit 的知道、相信和披露状态。

这让信息泄露检查和视角编译将来有明确数据来源，而不必把角色知识塞进 Person 的 JSON 字段。

### 3.9 最后补上可执行的一致性边界

所有当前态专表携带 `project_id + casefile_id + draft_id`，用复合外键防止跨项目、跨 CaseFile 或跨 Draft 串联。状态使用 `VARCHAR + CHECK`，重要的跨表类型门禁、乐观锁、Snapshot/Canon 确认门禁和不可变历史由 PostgreSQL 触发器执行。

迁移按依赖顺序拆成五段单链：

1. User 与 Project。
2. CaseFile、Draft、对象注册、引用和 Operation。
3. Entity、Person、Location、Event、Information Unit、Evidence、Testimony。
4. Phase、Knowledge、Claim、Hypothesis、Reasoning、Resolution、Constraint。
5. Snapshot、Canon、Audit、循环外键和触发器。

迁移文件使用 `VyyyyMMddHHmmss__lower_snake_case.py`，时间戳为 Asia/Shanghai 真实时间；大写 `V` 只存在于文件名前缀，Alembic `revision` 使用对应的 14 位时间戳。

## 4. 为什么最终恰好是 28 张表

| 层次 | 表数 | 表 |
|---|---:|---|
| 身份、所有权与编辑 | 7 | `users`、`projects`、`casefiles`、`drafts`、`casefile_objects`、`casefile_refs`、`draft_operations` |
| 叙事、实体与信息 | 11 | `narrative_phases`、`entities`、`people`、`locations`、`events`、`information_units`、`evidence_items`、`testimonies`、`claims`、`knowledge_states`、`knowledge_state_entries` |
| 推理、结论与约束 | 7 | `hypotheses`、`reasoning_paths`、`reasoning_nodes`、`reasoning_edges`、`resolution_specs`、`resolution_slots`、`casefile_constraints` |
| 版本与审计 | 3 | `draft_snapshots`、`canon_versions`、`audit_events` |
| **合计** | **28** | 不含 Alembic 自身版本表，也不含未来模块。 |

“28”不是长期不可改变的产品指标，而是当前明确需求的结果。未来出现新的独立生命周期、强约束或高价值查询时，可以通过新的时间戳迁移增加表；不能为维持数量而把新职责硬塞进旧表。

## 5. 方案对比

| 方案 | 优点 | 主要代价 | 结论 |
|---|---|---|---|
| 单一完整 JSON 文档 | 结构直观，写入和导出简单，Schema 演进快。 | 局部更新、关系完整性、并发控制、查询和索引困难；历史容易与当前态混在一起。 | 不选作当前态；仅用于不可变 Snapshot/Canon。 |
| 对象注册表 + 通用 `payload_jsonb` | 表少，新类型接入快，适合原型验证。 | 正文结构隐蔽，数据库难约束类型和关系，开发者理解、查询及迁移成本后移。 | 已放弃。 |
| 每种对象和每种关系都建专表 | 约束和查询最强，关系语义最显式。 | 表与迁移数量迅速膨胀；Schema 自定义关系难扩展；大量低价值连接表。 | 只用于稳定核心关系，不全量采用。 |
| **当前混合方案** | 核心字段可见、关键关系可约束、跨类型关系可扩展、正式版本可复现。 | 表较多；读取完整对象需要组合；Snapshot Builder 必须做可靠映射。 | **采用。** |

## 6. 关键技术选择与接受的代价

### 6.1 BIGINT Identity，而不是 UUID 或额外 public_id

选择自增 BIGINT 是因为当前为单 PostgreSQL 主库、个人产品底座，事务内插入和连接简单，索引也更紧凑。代价是内部 ID 不适合直接暴露为跨系统领域标识，因此 CaseFile JSON 只输出 `casefile_objects.object_id`，不输出关系主键。

如果未来出现多主离线写入、客户端先生成 ID 或跨区域无协调合并需求，需要重新评估分布式 ID；在此之前不为假设需求承担双 ID 成本。

### 6.2 专表是当前态事实源，JSONB 只保存开放叶子

身份、状态、版本和引用必须是关系字段。traits、geo、时间表达式、规则表达式、动态 Slot 值等尚未稳定且本身是小型树结构的内容可以使用 JSONB。

收益是重要约束可由数据库执行；代价是增加字段时需要 Alembic 迁移。这个代价是有意接受的，因为明确的迁移比隐藏在异构 `payload_jsonb` 中的隐式 Schema 更容易评审、测试和回滚。

### 6.3 VARCHAR + CHECK，而不是 PostgreSQL ENUM

CHECK 同样能拒绝非法状态，又能通过普通迁移较容易地添加或调整状态。代价是类型不会在数据库中复用成一个全局 Enum；项目用统一命名、ORM 和测试控制一致性。

### 6.4 数据库触发器与应用校验共同负责

数据库负责任何写入方都不得绕过的规则：归属、类型一致、revision 推进、不可变历史和 Canon 事务门禁。应用将来负责 CaseFile JSON Schema、RFC 8785 规范化、Snapshot 组装和用户可读错误。

触发器提高了一致性，但也增加调试和迁移复杂度。因此只把跨表原子规则放入触发器，不在触发器中实现 Snapshot Builder 或领域推理。

### 6.5 当前不启用 RLS、全文索引、GIN、PostGIS 或 pgvector

Repository 将来必须从 `owner_user_id` 开始过滤；当前个人版先不启用 RLS。搜索、空间和向量访问模式也尚未由真实查询验证，所以不预建专项索引。代价是后续需求成立时需要新迁移；收益是避免错误索引、写放大和运维复杂度。

### 6.6 Operation、Snapshot、Canon、Audit 都只追加

不可变记录能支持并发解释、确认复现和责任审计，但会持续增长。第一版接受存储增长，不用 UPDATE/DELETE 换取历史可信度；未来数据保留和物理清除必须使用独立、可审计的生命周期设计。

## 7. 一条事实怎样穿过这些表

以“门禁日志支持林舟有作案机会”为例：

1. 林舟先注册为 `casefile_objects(object_type='entity')`，正文写入 `entities`，人物扩展写入 `people`。
2. 门禁日志注册为 `casefile_objects(object_type='information_unit')`，通用正文写入 `information_units`，证据类型写入 `evidence_items`。
3. “林舟有作案机会”注册为 `claim`，断言正文写入 `claims`。
4. 门禁日志到 Claim 的支持关系写入 `casefile_refs(ref_kind='supports')`。
5. 一条 Reasoning Node 引用门禁日志，另一节点表达中间结论，两者用 `reasoning_edges` 连接。
6. 编辑动作写入 `draft_operations` 并推进 Draft revision。
7. Snapshot Builder 将当前专表和引用边组装为完整 CaseFile JSON，写入 `draft_snapshots`。
8. 所有者确认后，完全相同的 JSON 和哈希进入 `canon_versions`，同时产生 `audit_events`。

这条链说明：关系表用于可靠编辑和约束，完整 JSON 用于冻结与交换，两者不是互相竞争的两份事实源。

## 8. 何时应该新增字段、引用或新表

面对新需求时按以下顺序判断：

1. 它只是某张现有表的稳定单值属性：在该专表新增关系字段并创建时间戳迁移。
2. 它是稳定的单值对象关系：使用带 Project/CaseFile/Draft 归属的复合外键。
3. 它是跨类型、多值、有顺序或携带关系属性的对象关系：优先评估 `casefile_refs`，并为稳定 `ref_kind` 增加端点校验。
4. 它是开放、低约束的小型叶子结构：放入已明确允许的 JSONB 字段，并由 Schema 校验。
5. 它拥有独立生命周期、多个强约束、独立查询价值或一对多子项：建立新表，而不是塞入 JSONB。
6. 它属于认证、导入、素材、Validator、Compiler、团队协作等后续模块：在对应模块启动时单独设计，不修改当前表来预占位置。

任何数据库结构变化都应同步修改 ORM、时间戳 Alembic 迁移、数据库测试、受 Git 跟踪的迁移职责说明和本地字段说明。

## 9. 已知代价与缓解方式

| 代价或风险 | 缓解方式 |
|---|---|
| 28 张表增加认知成本。 | 按四个职责模块组织 ORM、五段迁移和文档；开发时先识别所属层次。 |
| 读取 Person、Evidence 等完整对象需要 JOIN。 | 由未来 Repository 封装固定查询，不让 API 层自行拼接。 |
| 专表演进会增加迁移数量。 | 使用大写 `V` + Asia/Shanghai 真实时间戳单链，并执行 `base → head → base → head`。 |
| `casefile_refs` 允许未来自定义类型，数据库无法提前理解全部语义。 | 数据库验证已知类型；应用写入前由 CaseFile JSON Schema Validator 验证自定义类型。 |
| 关系当前态和完整 Snapshot 之间可能映射错误。 | 未来 Snapshot Builder 使用确定性排序、JSON Schema 校验、RFC 8785 和 SHA-256，并建立往返与黄金样例测试。 |
| 触发器中的跨表规则不如应用代码直观。 | 只保留不可绕过的一致性规则，迁移 README 记录职责，集成测试直接验证失败路径。 |

## 10. 重新评估条件

出现以下情况时，应创建新的设计决策和时间戳迁移，而不是静默改变本决策：

- 产品正式启动多人共享、成员权限或团队审批，需要重新设计 Workspace/Membership 边界。
- 出现多主、离线优先或跨区域无协调写入，BIGINT Identity 不再满足标识生成要求。
- 某类 JSONB 叶子成为高频过滤、排序或强约束对象，应提升为正式列或投影表。
- `casefile_refs` 中某种关系形成独立生命周期或大量专属属性，应升级为专用关系表。
- 真实查询证明需要全文、GIN、空间或向量索引。
- 一个 CaseFile 需要多个并行 Draft 或分支合并，当前 1:1 Draft 模型不再成立。
