# 代码质量与 Git 提交规范

本文涵盖所有变更必须遵守的代码质量标准和 Git 规范。

## 代码规模

- 受 Git 跟踪且人工维护的每个源文件（含测试）不得超过 2000 行代码；接近 1500 行时必须评估并按职责拆分。机器生成文件、锁文件和外部规范原文不计入，但不得以"生成"为名规避拆分。

## 复用与抽象

- 新增函数前必须检索现有语义一致的实现；能够直接复用时不得重复实现，能够通过小幅、清晰扩展复用时优先扩展。不得为了表面去重合并语义不同、生命周期不同或变化原因不同的逻辑。
- 创建或修改函数时必须同时考虑职责单一、命名准确、输入输出明确、可测试性、合理通用性和后续扩展点。只为已经存在或可以明确预见的变化保留扩展能力，禁止没有实际需求的过度抽象。
- 模块必须有明确、稳定且互不重叠的职责；依赖方向保持单向，下层模块不得反向依赖上层实现，禁止循环依赖、跨层访问内部细节和无明确归属的通用 `utils`。
- 模块间联动必须通过最小、明确的公开接口、类型或契约完成；避免隐式全局状态、导入副作用和需要多处同步修改的耦合。一次业务变化若持续牵动多个无关模块，应先调整边界再继续扩展。

## 测试要求

- 行为变更必须补充或更新对应测试，至少覆盖主路径和本次变更涉及的关键失败路径；修复缺陷时应优先增加能够复现问题的回归测试。
- 变更应保持范围聚焦，不夹带无关重构；公共契约、数据库结构、配置或运行方式发生变化时，必须同步更新测试、说明和兼容/迁移方案。
- 数据库结构变化必须同时提交 ORM、Alembic 迁移、测试和职责说明；只改其中一层视为未完成。

## Git 提交规范

- 提交标题必须使用 `<type>: <中文简要说明>`，冒号后的摘要必须为中文，不得使用纯英文提交摘要。
- `type` 按变更性质使用：`feat`、`fix`、`refactor`、`docs`、`test`、`build`、`chore`。
- 除前缀、文件名、代码标识符、协议名和专有名词外，标题与正文说明必须使用中文。
- 一次提交只表达一个完整目的；数据库迁移、模型、契约、测试和职责文档需要同步变更时，应作为同一个完整目的提交。
- 提交意图和影响必须清楚说明，不得只写英文前缀或模糊描述。
