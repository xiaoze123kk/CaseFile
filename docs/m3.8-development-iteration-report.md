## 1. 结论

M3.8 已完成从“单次有界 Goal 执行”到“跨消息、跨执行切片的持久化协作”的后端开发，并通过完整质量门禁和正式 Interactive Goal qualification。

- `qualification_outcome=passed`、`qualified=true`；基础设施失败 0，全部禁止效应/安全违规计数 0，19 项正式 gates 全部通过。
- 八个 family 最低为 8/9，22/24 个场景三次全通过；只读场景和此前失败的 Patch Apply Update 场景均为 3/3。
- 剩余两条提案拒绝仍计为功能失败，不删除、不挑选重跑、不用定向结果补分。
- 验收通过不等于默认上线：`CASEFILE_CHAT_GOAL_SESSION_ROLLOUT` 默认仍为 `off`，本次 PR 不激活生产环境、不实现前端，也不合并 PR。

这次优化不是单纯“换提示词后成功率升高”。它同时修复了运行时语义、原子续跑、失败状态收敛和评测归因。尤其是上一轮 98.61% 未通过、最终 97.22% 通过，说明资格来自完整证据和硬边界，而不是只看最高分。

### 始终保留的架构约束

- TaskRun 仍只有原有六种状态；waiting/stale/superseded 属于 GoalSession，不以长时间占用 Worker lease 模拟等待。
- 控制消息必须显式指定模式；服务端拥有状态机、预算、证据复用和 lineage 权威，模型只提出 typed 语义草案。
- 安全点只位于 Controller 前、完整 capability 后、Finalizer 前，不强制中断 Provider、Binder、Simulation、Verification 或 Apply 事务。
- 正常 steer 把旧切片收敛为 `succeeded + checkpointed`，而不是 cancelled；保存 Checkpoint、消费单条消息、追加 Revision、创建唯一 continuation 必须同事务完成。
- Patch 写入仍走 General Mutation / VerificationEngine / 显式审批 / V1EditingService；禁止自动 Apply、自动 rebase、跨 Project、多 Agent 和无限循环。
- 会话上限固定为 8 revisions、12 slices、6 次已消费 steer/replace；不能用续跑绕过预算。

## 3. 评测为什么先被修复

### 3.1 从可执行 harness 到可用于验收的 v2

早期 v1 运行已在架构记录中判定污染并冻结为无效，本报告不使用其分数作为基线，也不补造一个“可用结论”。随后 v2 加入：

- 24 场景、8 family 各 3 场景；三类安全点、混合 FIFO、提前 follow-up 拒绝、增删义务、三类 PatchOperation、至少三个 fixture 和完整等待/取消/过期生命周期覆盖。
- 默认关闭的 `GoalSafePointObserver` 与确定性 barrier，通过公共 API 注入消息，不以固定 sleep 猜测安全点。
- Worker 只 claim 已知 TaskRun，避免同库其他 trial 的全局 FIFO 干扰。
- 私有题包与独立 reviewer attestation、Reference replay、descriptor 指纹匹配；公开 Fake suite 只承担开发回归。

### 3.2 不能把所有失败叫作模型能力不足

初次 v2 报告同时存在执行器异常、投递未完成、Amendment/Observation 不匹配和最终状态失败。逐 trial、数据库事件及 ModelCall 证据比总分更有诊断价值。

`9d8c4b3` 中修正了两类评测归因问题：

1. 合法 General Mutation 子组件使用自己的 Prompt 版本，不能误判成 Chat Prompt 漂移；仍限制为已知合法组件，不接受任意版本。
2. Observation invalidation Oracle 不匹配与“实际复用了无效 Observation”分开记录。前者仍是语义失败，但不能在 `reuse_invalid=0` 时凭空增加安全违规。

因此，早期与后期分数不是严格受控的单变量实验。旧报告中的原始指标保持原样，不按新规则回填历史分数。

## 5. 关键迭代：问题、根因、修复与验证

### 5.1 凭据和错误可观测性（`6133340`、`35eb0c0`）

保存凭据不可用时，任务在底层已失败，但外层仍可能等待安全点，从而把认证故障表现成 safe point 或 missing task 错误。修复改为从本机环境读取精确 Pro 凭据，保留稳定执行器错误原因并识别致命认证/4xx 故障。隔离 worktree 也必须注入保存 Provider 设置所需的加密主密钥。

本层故障发生在有效能力评测之前：72 条失败不能说明模型“成功率为零”。凭据正文从未写入本报告或 PR；私有题包和原始运行目录不提交。

### 5.2 语义契约与 v18 → v19 → v20（`9d8c4b3`、`bd16432`）

- v18 建立独立 Amendment 组件及来源摘录校验。
- v19 明确自包含义务摘录、refine 重算与目标约束，修正旧 Oracle/组件身份归因。
- v20 强化 Amendment 的结构差异分类，并允许续跑后只剩一个义务时构造合法 Finalizer 输入。

历史 Prompt 包保持不可变；新版本只在相应 GoalSession 路径选择。此次阶段性结果升至 57/72，但多个 family 和安全点仍未达标，所以没有提前宣告验收。

### 5.3 安全点、义务与 Observation（`523b603`）

问题包括：模型遗漏 grounding 前置分析、重复选择已完成义务；禁止性约束被误投影成替换义务；收窄范围后旧 Observation 未按需要重算；Mutation 后收到 steer 时缺少已经持久化的 PatchSet identity。

修复把可证明的规范化放在服务端：保守使用作者完整消息作为摘录兜底、补齐必要 grounding、改选 DAG-ready 未完成义务、已满足时直接进入 Completion Gate；明确区分 add_constraint 与 refine 对复用身份的影响。

Mutation 后的 steer 不伪造证据身份：先自然完成 PatchSet 待审切片，显式 Apply 后的 post-apply slice 在任何新 capability 前消费等待的 steer。结果提高至 64/72，但新的完整证据显示 clarification 和投递收敛仍有缺陷。

### 5.4 澄清与干预归一化（`b65dd66`）

明确作者审批门控的修改目标被规范为可达的 `analysis → audit → mutation` 顺序；未解析指代确定性进入 clarification；明确无修改的澄清去掉 mutation/candidate 义务；收窄范围不因模型输出 remove/refine 的差异而错误改变义务形状或复用旧结果。

完整结果为 65/72。它达到总通过条数下限，但仍有三条基础设施失败及其他未完成记录，说明“总分及格”不能替代逐层门禁。

### 5.5 续跑漂移与只读回归（`e6da25b`、`18c4a5d`）

`e6da25b` 补齐明确请求中的缺失义务，处理“放弃 X、保留 Y”、replace 自包含目标及 Finalizer 公共语言失败收敛。但补齐规则引入回归：否定句里的“修改”关键词被当成正向修改请求，生成了并未获授权的 mutation obligation。

read-only 连续三次失败不是可以忽略的偶发波动。`18c4a5d` 通过 `_requests_no_mutation` 与初始义务规范化修复：显式只读时移除模型臆造的修改义务，并禁止关键词补齐把它再次加回；补充单元与真实 executor 回归。

新全套结果为 71/72，只读恢复 3/3。剩余 missing-task 仍使正式资格失败，不能把 98.61% 宣称为已通过。

### 5.6 从“任务丢失”追到生产失败收敛（`741c304`）

对 `18c4a5d` 失败现场的检查确认：TaskRun 173 因 `goal_capability_blocked` 失败，Planner/Binder 留下 `general_mutation_field_forbidden`；Goal 71 与 capability Step 却仍为 running。随后 executor 再寻找活跃任务，才抛出 `interactive_goal_task_missing`。

保留的五次 ModelCall 均显示调用成功，但成功 Planner 原文未留存，无法恢复具体被拒字段。因此能确认的是“提案被 Binder 拒绝 → TaskRun 失败 → Goal/Step 未收敛 → harness 掩盖原始错误”，不能断言具体字段，更不能把它简单归为网络抖动。

本次修复分为两部分：

1. **生产链路**：在现有 lease/Attempt fencing 的 TaskRun 失败事务中，通过 WorkflowService 同时关闭当前 Goal、active slice、残留 running Step，并取消 queued/claimed control 及相应 pending 回复；不改写终态或旧 Revision 的 Goal。
2. **评测链路**：持久化任务失败与真正 harness/transport 异常分开，采集完整公共快照和审计，记录 `task_failed:<code>`、`mutation_blocked:<reason>`；失败继续计入分母，不转换成成功。

以合法 Schema 但非法修改字段的 Fake 提案先复现，再覆盖“等待状态/Finalizer 前 × 有/无排队 steer”四种组合。相关回归 107/107；原失败场景独立 Pro 3/3；最后重新执行完整 72 条，而不是拼接这 3 条诊断结果。该提交不修改 Prompt、Binder 权限、Oracle 或正式聚合门槛。
