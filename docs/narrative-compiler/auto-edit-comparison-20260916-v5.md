# 自动审编 v14 真实评测报告

结论：`prose-shadow-runtime-v14` 已修复 Judge 协议可靠性，自动审编 6/6 完成交付与审核，
连续三场景也完成 3/3；在两模式共同交付的 5 个场景上，自动审编减少 50.0% 请求、43.8%
Token、24.7% 耗时和 41.9% 估算费用。匿名换序质量比较没有证明自动审编质量更好：完整精修
稳定胜 1 组，自动审编稳定胜 0 组，4 组顺序不一致。

## 冻结方法

- 本轮标识 `20260916-live-v5`，模型 `deepseek-flash`，runtime
  `prose-shadow-runtime-v14`，协议 `prose-auto-edit-json-object-v2`。
- 使用与 v4 相同的公开 Writer 开发集索引 `0, 3, 6, 9, 12, 15`；suite hash
  `d32d741fc9d98418b1e6fe2d100859d472f9e2af1b7af92e7a7f7250c43718d9`。
- 冻结两个模式的 runtime、Prompt、完整输入与 1,293 个源文件哈希；结束后复核无变化。
- 正文通过生产 `ProseShadowExecutor._scene`、`DurableProseProvider` 和 PostgreSQL
  `ProseStore` 串行执行。假规划器只建立隔离任务，不计入模型成本。
- 每组各运行一次，不重跑失败项。两份交付稿交换 A/B 顺序比较两次；两次归一化偏好不一致
  记为顺序不一致，不强行选胜者。
- 真实调用前的 Fake Provider 预检确认 v14、v2 协议和强制数组 Schema 已进入生产账本。

## 自动审编行为

- 6 场全部走完 Writer → Judge → Rewrite → Judge，每场恰好 4 次请求；协议失败、技术回退、
  未知用量均为 0。
- 首次 Judge 6/6 都选择 `full_rewrite`，没有选择 retain 或 polish。最终 Judge 选择原稿 4 场、
  修改稿 2 场。说明 Rewrite 并非天然成为最终稿，匿名回选确实发生作用；本样本没有真实覆盖
  Polisher 路径。
- 每场最终报告仍保留 2–3 个未解决问题，共 14 项。`strict_semantic_pass` 为 4/6，产品交付
  与严格语义状态保持分离。
- 完整精修交付的 5 场均记录 `quality_unstable` 并保留原稿，没有采用 Polisher 候选。

| 结果 | 组数 |
|---|---:|
| 自动审编稳定胜 | 0 |
| 完整精修稳定胜 | 1 |
| 平局 | 0 |
| 交换顺序后不一致 | 4 |
| 无法比较 | 1 |

唯一稳定结果出现在 Beat 实现场景，偏好完整精修。事实依据、披露控制、时空连续性与因果顺序
四组都对候选顺序敏感，而且四组在两次比较中都选择了当次排在 A 的候选，表现为一致的首位
偏差。有效 JSON 不等于稳定判断：当前 A/B 结果不能证明自动审编改善文学质量，也不能把 4 组
不一致算成平局。评估自身使用 10 次请求、93,978 Token、25.057 秒，估算 ¥0.193020。

## 验收判断

- Judge 协议修复：通过。9 个自动审编场景均完整审核，0 协议失败，v4 的 0/9 审核完成问题
  没有复现。
- 有界流程与产品交付：通过。本轮没有越过 4 次正常修改路径，也没有服务端文学选稿。
- 成本与耗时：在共同交付的 5 场中明显低于完整精修。
- 文学质量收益：未通过证明。稳定偏好没有支持自动审编，而且 4/5 可比较组存在顺序效应。
- 人类阅读质量：未评估；模型偏好不能替代该结论。

因此，新模式已经达到“可靠完成模型审编，并以更低资源交付”的工程目标；本轮证据不支持
“质量优于完整精修”的主张。
