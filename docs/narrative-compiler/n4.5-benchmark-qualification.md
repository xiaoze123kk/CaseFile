# N4.5 Benchmark 与资格协议

## 文档状态

本文冻结 N4.5-00 的 Judge、Writer、Rewrite、Quality 与完整 E2E 资格协议。总体运行边界见
[`n4.5-prose-rendering-architecture.md`](n4.5-prose-rendering-architecture.md)，字段与证据协议见
[`n4.5-agent-judge-protocol.md`](n4.5-agent-judge-protocol.md)。所有门槛必须在任何对应 live 运行前冻结，不能根据正式结果追认。

N4.5 Benchmark 的 Gold 是 ScenePlan、Checklist 与人工 verdict，不是标准正文。文字不要求相同；语义必须正确，文学质量只在语义通过后独立评估。

## 评测层级

| 层级 | 被测对象 | 输入 | 是否 Provider | 是否资格门禁 |
|---|---|---|---:|---:|
| B0 | Semantic Judge、Consensus、Arbiter | 固定 ScenePlan/Checklist + 固定正文 + 人工 Gold | 是 | 是 |
| B1 | Writer | 固定 ScenePlan/Profile/context | 是 | 是 |
| B2 | Rewrite | 固定坏正文 + 固定 Judge findings | 是 | 是 |
| B3 | Quality Critic 与 Polisher | 人工偏好对、语义已接受正文 | 是 | 是 |
| B4 | 生产路径 E2E | CompileRun → ScenePlan → 最终正文 | 是 | 是 |

每层单独报告组件能力、基础设施失败、调用数、usage、latency 和 fingerprint。低层未通过时，不得用高层最终成功率掩盖，也不得启动依赖它的正式 live 层。

## B0 人工 Gold

### 能力矩阵

固定八个能力族：

1. `beat_realization`
2. `event_modality`
3. `reveal_control`
4. `pov_knowledge`
5. `location_time`
6. `causality_ordering`
7. `major_hallucination`
8. `implicit_semantics`

开发集共 24 条，每族固定：

- 1 条 `explicit_valid`。
- 1 条 `implicit_valid`。
- 1 条 `adversarial_invalid`。

私有 Holdout 共 48 条，每族固定：

- 1 条 `explicit_valid`。
- 2 条 `implicit_valid`。
- 3 条 `adversarial_invalid`。

因此 Holdout 固定包含 24 条合法和 24 条关键非法正文，其中 16 条为隐含合法正文。

每条基础样本必须人工冻结：

- 完整 ScenePlan/Checklist 输入。
- 原始 prose。
- 每个 check 的 Gold verdict。
- Scene Gold verdict。
- error tags 与 critical 标记。
- 一份 semantic-preserving paraphrase 及其不变 verdict。
- 一份 semantic-changing mutation 及变化后的 check/Scene verdict。
- 人工 reviewer identity、review timestamp、review policy version 与 attestation hash。

Mutation 至少覆盖：发生→考虑、肯定→否定、正确主体→错误主体、允许 Reveal→提前 Reveal、正确地点/时间→漂移、正确顺序→因果倒置、删除 required Beat、增加重大状态变化。Paraphrase 至少覆盖同义改写、显式→隐式、句序调整、对白/叙述互换和无语义影响的感官细节。

另冻结 16 组私有 Arbiter 冲突用例。每组包含完整 Checklist/正文、两个或三个相互冲突但结构合法的 Judge assessments、人工 Gold 裁决和 critical 标记。它们不依赖正式 Council 是否自然产生分歧。

### 私有 Holdout 边界

开发集、生成脚本和公开 Fake 用例可以提交。以下内容不得进入 Git：

- 48 条 Holdout 正文及其变体。
- check/Scene Gold labels。
- 16 组 Arbiter 冲突正文与裁决。
- reviewer 原始表单与未脱敏身份信息。

仓库只提交 fail-closed descriptor，记录 suite schema、task count、能力分布、variant count、内容 hash、review policy、attestation hash 和允许的 loader version。正式 Runner 必须通过显式 `HoldoutPath` 读取私有包；缺失、hash 不符、分布不符、重复文本、review 不完整或路径位于仓库受跟踪范围内时，在任何 Provider 调用前 blocked。

## Council 消融与冻结

只在 24 条开发集上按固定顺序比较：

1. `fidelity-only-v1`。
2. `fidelity-adversarial-arbiter-v1`。
3. `fidelity-adversarial-coherence-arbiter-v1`。

所有候选使用同一 `deepseek-v4-pro`、同一 Checklist、相同最大输出预算和各自冻结 Prompt。每个候选必须完整运行全部开发样本、paraphrase 和 mutation，不能用不同样本或选择性重试比较。

开发门槛：

- Overall ≥ 22/24。
- 8 条关键非法 false accept = 0。
- 8 条隐含合法通过 ≥ 7。
- Semantic-changing detection ≥ 23/24，critical miss = 0。
- Paraphrase invariance ≥ 23/24。
- 所有非空 evidence 精确绑定率 100%。
- 基础设施失败 0。

选择规则：

1. 排除任一开发门槛失败的候选。
2. 在剩余候选中选择每基础样本模型请求数中位数最低者。
3. 请求数相同时按上述候选顺序选择角色更少者。
4. 冻结选中 policy 的角色、Prompt/Schema/Model hash、Consensus/Arbiter policy、输出预算和开发报告 hash。
5. 冻结后才允许执行一次私有 Holdout。

Holdout 不参与选择。正式失败后不得查看具体原题继续修改同一 Suite 的 Prompt；任何修复必须形成新的 Prompt 与 Suite/descriptor version，重新运行完整开发选择和新的完整 Holdout attempt。

## B0 Holdout Gate

一次正式 Judge attempt 必须完整运行 48 条基础样本、48 条 paraphrase、48 条 semantic-changing mutation 和 16 条 Arbiter 冲突用例。

全部硬门槛：

| 指标 | 门槛 |
|---|---:|
| 基础样本 Overall | ≥ 44/48 |
| 关键非法 false accept | 0/24 |
| 隐含合法通过 | ≥ 15/16 |
| Semantic-changing detection | ≥ 46/48 |
| Critical mutation miss | 0 |
| Paraphrase invariance | ≥ 46/48 |
| Arbiter accuracy | ≥ 15/16 |
| Arbiter critical wrong | 0 |
| 非空 evidence 精确绑定 | 100% |
| 协议遗漏/额外 check | 0 |
| 基础设施失败 | 0 |

`qualified=true` 只有在全部门槛同时满足时产生。综合平均分、模型 confidence、质量分或成本不能抵消硬门槛失败。

## B1 Writer 资格

Writer Suite 固定为八个能力族 × 三个 variant，共 24 Task：

- `basic`：短上下文、直接 obligation。
- `implicit-friendly`：允许通过行为、潜台词或省略实现，但不得弱化事件模态。
- `constraint-dense`：多个 Beat、状态、Reveal、时间/地点和因果要求同时存在。

每个 Task 必须冻结 ScenePlanIR v2、NarrativeIR、NovelProfile v2、前一场已接受正文或 `null`、Checklist hash 和输入证据路径。Writer 不读取 Reference prose。

组件正式运行固定 24×3=72 trials。每个 trial 输出初稿后，只由已通过 B0 的冻结 Council policy 评审。记录：

- initial semantic pass。
- pass@3 与 all-three。
- 每个 check kind 的通过/失败。
- critical violation、Judge disagreement 和 Arbiter frequency。
- 字符数、tokens、latency 和 cost。

Writer 资格门槛在 B4 E2E 中一并判定：初稿 ≥65/72、pass@3 24/24、all-three ≥20/24。

## B2 Rewrite 资格

固定 24 个由人工审定的坏正文，每个包含一份原始 SceneRender、完整 Checklist、合法 Consensus findings 和此前通过项目。错误分布必须覆盖：

- 缺失 required Beat。
- 发生/决定被弱化为计划、考虑、假设或可能。
- 提前 Reveal。
- 错误主体、知识、地点或时间。
- 因果/顺序倒置。
- 重大新增剧情。
- 多错误组合。

每个用例分别运行 Rewrite 1；仍失败的用例允许 Rewrite 2。每轮后使用冻结 Council 复审全部 check。

硬门槛：

- 原问题移除并最终通过 ≥21/24。
- 原来通过的语义保持 ≥23/24。
- 新增关键问题 0。
- 第二轮后额外 Rewrite 调用 0。
- 协议与基础设施失败 0。

报告必须分别给出 Round 1 rescue、Round 2 incremental rescue、未修复原因与新增问题，不得只报告最终总成功率。

## B3 Quality 与 Polish 资格

v1–v3 的双位置 Pairwise 与整篇 Polisher 只保留历史重放。B3 v4 固定 8 组公开开发对、
16 组私有 Holdout（32 份匿名单稿评估、其中 4 组中性变体）和 24 个局部 Polisher Scene。
两份正文必须通过同一 Semantic Checklist 并保持直接 lineage；Quality 模型不接收
original/polished/A/B 身份，只输出五维 `none|low|medium|high` 与服务端 Evidence ID。

Quality Assessment 与确定性 Delta 门槛：

| 指标 | 门槛 |
|---|---:|
| 160 个维度 severity 精确正确 | ≥144/160 |
| Delta 接受/回滚正确 | ≥15/16 |
| 五维完整覆盖与 Evidence 有效 | 32/32 |
| 中性变体五维稳定 | 4/4 |
| 协议或基础设施失败 | 0 |

Polisher 只能修改服务端由 Evidence 派生的最多 3 个窗口，总覆盖不超过正文 40%；超限、
空补丁、Preservation 非 pass 或 Delta 未改善均精确回滚原稿。24 Scene 门槛：

- Patch 契约合法且窗口外逐字节不变 24/24。
- Preservation Council 通过 24/24。
- 最终正文 quality non-loss 24/24。
- 至少 18/24 达到目标维度改善并被 Delta 接受。
- 被采用润色稿的关键语义回退 0。
- 未采用润色稿回滚到精确原稿 100%。

Quality Critic 未通过资格时，Polisher 不进入 B4；Writer/Rewrite 可以保留组件报告，但不能宣称完整 N4.5 qualified。

## B4 生产路径 24×3 正式资格

B4 必须从真实 CompileRun、Worker、PostgreSQL、AgentStepRun、AgentModelCall 和 CompileArtifact 路径执行。纯内存 Runner、FakeProvider 或组件报告不能替代。

运行身份：

- 生成、Semantic Judge、Arbiter、Rewrite、Quality Assessment、Patch Polisher：`deepseek-v4-pro`。
- 24 Task × 3 trials = 72。
- `preview + prose_renderer_shadow=true`。
- clean Git revision、独立 disposable `_test` PostgreSQL、全新 TaskRun/Attempt。
- 允许 checkpoint 只恢复同一 attempt 内完整 fingerprint 相同的成功调用；不得混入其他 revision 或报告。

全部硬门槛：

| 指标 | 门槛 |
|---|---:|
| 完整 trials | 72/72 |
| Writer 初稿 semantic pass | ≥65/72 |
| Writer 初稿 pass@3 | 24/24 |
| Writer 初稿 all-three | ≥20/24 |
| 最终接受正文 | ≥71/72 |
| Final pass@3 | 24/24 |
| Final all-three | ≥23/24 |
| 被接受正文关键语义违规 | 0 |
| Rewrite 超过两轮 | 0 |
| 被采用润色稿关键回退 | 0 |
| 失败润色精确回滚 | 100% |
| Provider/协议/持久化/harness 基础设施失败 | 0 |
| 证据绑定、调用 lineage、Artifact hash 漂移 | 0 |

只有全部 B0–B4 Gate 通过，正式报告才允许：

```json
{
  "qualification": {
    "status": "qualified",
    "qualified": true,
    "eligible_mode": "preview_explicit_shadow"
  }
}
```

资格不改变 Shadow 默认关闭，不授权 canonical、自动采用、前端发布或必经编译。

## Attempt、失败与重跑规则

正式 attempt 必须不可变保存成功、语义失败、协议失败和基础设施失败。规则如下：

- 能力或安全失败不得替换、删除或选择性补跑。
- 基础设施失败使整次正式 attempt 为 `inconclusive_infrastructure`，不能从已有成功 trial 拼接资格。
- 可以发起全新的完整 attempt，但必须保留旧 attempt、failure evidence、usage 和 fingerprint。
- 修改代码、Prompt、Schema、Model、Profile、Council policy、Suite、Holdout、门槛或 reviewer label 后，旧 attempt 只能作为历史诊断。
- Partial、focused、same-sample、Fake、Flash 生成或不完整数据库路径只能标记 diagnostic/smoke。

## 正式证据与报告

每份正式报告必须冻结并校验：

- Git revision、branch、dirty state 与受跟踪 source fingerprint。
- 数据库 revision、数据库名称 `_test` 门禁与迁移 head。
- Suite、Holdout descriptor/content、review policy、reviewer attestation 和输入 hash。
- Profile、ScenePlan、NarrativeIR、Checklist policy、Council policy、Prompt、Schema、runtime、Provider 和 Model hash。
- 每个 Task/Trial/Scene/round 的 Step、Call、Artifact lineage。
- 原始响应保留策略、结构化错误、evidence、usage、latency、requests 和成本。
- 全部 Gate 输入值、逐项结果、资格状态与报告自哈希。

报告不得保存 API key、解密配置、私有 Holdout 正文或未脱敏 reviewer 身份。凭据只从本地已保存配置读取到内存。

## 阶段停止点

- B0 Fake/结构门禁未通过：不调用 live Judge。
- B0 开发候选均未通过：不运行 Holdout。
- B0 Holdout 未通过：不开始 Writer live 资格。
- Writer 组件门禁未通过：不开始 Rewrite live。
- Rewrite 门禁未通过：不开始 Quality/Polish live。
- Quality Critic 未通过：不开始完整 B4。
- B4 任一硬门禁失败：保持 Preview Shadow 默认关闭并停止，不用聚合分数覆盖失败。

24×5/10 Stability、跨模型族 Council 和扩大产品 rollout 不属于本资格协议。
