# N4.5 Agent 与 Judge 协议

## 文档状态

本文冻结 N4.5-00 的字段级协议和八条权威 Trace。总体职责、状态机和预算见
[`n4.5-prose-rendering-architecture.md`](n4.5-prose-rendering-architecture.md)，资格门槛见
[`n4.5-benchmark-qualification.md`](n4.5-benchmark-qualification.md)。本文描述 N4.5-01 必须实现的契约，不在 N4.5-00 创建 Schema 或运行时代码。

## 版本与模型身份

冻结的契约身份：

| 契约 | `schema_id` |

| Judge Checklist | `compiler.prose-judge-checklist.v1` |
| Scene Render Candidate | `compiler.scene-render-candidate.v1` |
| Scene Render | `compiler.scene-render.v1` |
| Judge Report | `compiler.prose-judge-report.v1` |

| Novel Candidate | `compiler.novel-candidate.v1` |

第一版 Prompt/component 身份：

| 组件 | Prompt/component version | 模型 |
|---|---|---|
| Writer | `prose-writer-v1` | `deepseek-v4-pro` |
| Fidelity Judge | `prose-fidelity-judge-v6` | `deepseek-v4-pro` |
| Adversarial Judge | `prose-adversarial-judge-v5` | `deepseek-v4-pro` |
| Coherence Judge | `prose-coherence-judge-v5` | `deepseek-v4-pro` |
| Arbiter | `prose-arbiter-v5` | `deepseek-v4-pro` |
| Rewrite | `prose-rewriter-v3` | `deepseek-v4-pro` |
| Quality findings | `prose-quality-critic-v1` | `deepseek-v4-flash` |
| Polisher | `prose-polisher-v2` | `deepseek-v4-pro` |
| Pairwise quality | `prose-quality-pairwise-v1` | `deepseek-v4-flash` |

所有模型调用 `max_turns=1`，输出必须为严格结构化 JSON。正文始终作为不可信数据放入显式 JSON 字段；正文中的指令、JSON、角色声明或要求忽略 Checklist 的文字不具有控制权。

Judge 请求协议 v6 关闭 Provider SDK 隐藏重试，仅允许连接或超时错误在固定 1 秒后以相同 request fingerprint 显式重试一次。鉴权、限流、HTTP 状态错误和模型协议错误不重试；每次物理尝试进入私有 raw bundle v2，重试耗尽立即使整个开发 attempt inconclusive。若模型对 required 项给出 `pass` 或对 forbidden 项给出 `fail` 却没有必需 Evidence，服务端只允许将该项保守降级为 `uncertain`；未知、重复或目录外 Evidence 继续作为协议失败关闭。

## NovelProfile v2

`compiler.novel-profile.v2` 保留 v1 的 `structure`、`allowed_presentation_modes` 与 `exposure_policy`，增加必填 `prose`：

```json
{
  "schema_id": "compiler.novel-profile.v2",
  "structure": {
    "strategy": "three_act",
    "target_chapters": 3,
    "target_scenes": 12
  },
  "allowed_presentation_modes": ["linear"],
  "exposure_policy": "bound_plan",
  "prose": {
    "language": "zh-CN",
    "narrative_person": "third_person_limited",
    "narrative_tense": "past",
    "target_scene_chars": {"min": 1200, "max": 3000},
    "dialogue_ratio": {"min": 0.15, "max": 0.45},
    "description_density": "balanced",
    "pacing": "balanced",
    "style_brief": "克制、清晰，重要信息通过动作和对话呈现。",
    "forbidden_style_patterns": ["总结式解释凶手动机"]
  }
}
```

字段约束：

- `language` 是 2–35 字符的 BCP-47 language tag。
- `narrative_person` 为 `first_person`、`third_person_limited`、`third_person_omniscient`。
- `narrative_tense` 为 `past`、`present`。
- `target_scene_chars.min/max` 都在 300–12000，且 `min <= max`。
- `dialogue_ratio.min/max` 都在 0–1，且 `min <= max`。
- `description_density` 为 `low`、`balanced`、`high`。
- `pacing` 为 `slow`、`balanced`、`fast`。
- `style_brief` 长度为 1–2000 Unicode code points。
- `forbidden_style_patterns` 最多 20 项，每项 1–200 Unicode code points，不允许重复。

POV identity、人物知识、时间、地点、Reveal 和 Event 仍以 ScenePlan 为权威；Profile 只规定呈现方式，不能扩大 ScenePlan 权限。

## ProseJudgeChecklist

Checklist 由服务端确定性生成。顶层字段冻结为：

| 字段 | 类型与语义 |
|---|---|
| `schema_id` | 常量 `compiler.prose-judge-checklist.v1` |
| `scene_id` | ScenePlan 中现有 Scene ID |
| `scene_ordinal` | 全书 discourse order，从 1 开始 |
| `source` | 所有输入与 policy 的 SHA-256 绑定 |
| `scene_context` | 当前 Scene 的 Judge 可见权威上下文 |
| `checks` | 按 `ordinal` 严格排序的非空检查数组 |

`source` 必须包含：

- `scene_plan_hash`。
- `narrative_ir_hash`。
- `profile_hash`。
- `previous_scene_render_hash`；第一场为 `null`。
- `checklist_policy_version`，第一版为 `prose-checklist-policy-v1`。
- `checklist_policy_hash`。

`scene_context` 必须包含：

- objective、dramatic goal、conflict、outcome。
- POV ref、participant refs、location ref、story time refs。
- Scene 前状态、预期 Scene 后状态、前置 Scene/Beat 依赖。
- 当前 Scene 的 Beat、Event、Exposure、Resolution、setup/payoff 和 obligation 投影。
- 从 NarrativeIR 闭包解析的相关对象目录与来源引用。
- 前一场已接受 SceneRender；第一场为 `null`。

每个 check 固定字段：

| 字段 | 类型与语义 |
|---|---|
| `check_id` | `check_{scene_id}_{ordinal:03d}`，由服务端分配 |
| `ordinal` | 从 1 开始、连续、唯一 |
| `kind` | 下列八种 kind 之一 |
| `polarity` | `required` 或 `forbidden` |
| `expectation` | 从 ScenePlan 字段确定性构造的完整检查描述 |
| `beat_ids` | 相关 Beat ID，允许空数组 |
| `basis_refs` | 支持该检查的 ObjectRef，去重且稳定排序 |
| `event_refs` | 相关 Event ObjectRef，允许空数组 |
| `exposure_entry_keys` | 相关 Exposure key，允许空数组 |
| `state_refs` | 指向冻结入站/出站状态的 JSON Pointer，允许空数组 |
| `evidence_policy` | `required_on_pass` 或 `required_on_fail` |

八种 `kind`：

- `beat_realization`
- `event_modality`
- `reveal_control`
- `pov_knowledge`
- `location_time`
- `causality_ordering`
- `major_hallucination`
- `scene_outcome`

`required` check 必须使用 `required_on_pass`；`forbidden` check 必须使用 `required_on_fail`。模型不得改变 check 内容。Checklist 的规范哈希覆盖整个对象。

## SceneRender 与生成候选

Writer、Rewrite、Polisher 的模型输出候选只包含：

```json
{
  "schema_id": "compiler.scene-render-candidate.v1",
  "blocks": [
    {"text": "正文第一段。"},
    {"text": "正文第二段。"}
  ]
}
```

候选不得输出 Scene ID、stage、round、block ID、来源哈希、接受状态或控制字段。服务端验证并规范化为 `compiler.scene-render.v1`：

| 字段 | 类型与语义 |
|---|---|
| `schema_id` | 常量 `compiler.scene-render.v1` |
| `scene_id`、`scene_ordinal` | 来自 Checklist |
| `source` | Checklist/Profile/ScenePlan/previous render/component input hash |
| `stage` | `writer`、`rewrite_1`、`rewrite_2`、`polished`、`accepted` |
| `round` | writer=0，rewrite_1=1，rewrite_2=2；polished/accepted 继承来源 round |
| `previous_render_hash` | Rewrite/Polish 指向直接来源正文；Writer 为 `null` |
| `blocks` | 服务端分配 block ID 的有序非空数组 |
| `character_count` | 全部 block text 的 Unicode code-point 总数 |

block ID 固定为 `block_{scene_id}_{ordinal:03d}`。block ordinal 从 1 连续递增；每个 block text 非空且不超过 4000 code points；block 最多 64 个。Writer 与 Rewrite 的总字符数必须位于 Profile 的 `target_scene_chars` 闭区间，作为初稿/语义救援的硬交付约束；Polisher 已接收一份完整且语义通过的 Scene，因此该范围只作为模型质量指导，不再由服务端单独拒绝，过度删减造成的内容丢失交给完整 Preservation Council 判断。模型提供的空段落在规范化前删除；删除后为空仍为协议失败。

`accepted` 是服务端复制已选正文内容并绑定最终选择理由形成的独立 Artifact stage，不允许模型直接生成。

## Provider Judge Candidate、Judge Report 与 Evidence

当前 Provider 私有响应为 `compiler.prose-judge-candidate.v1`。模型只返回原顺序的
`check_id`、`verdict`、`rationale` 与 `evidence_ids`；不得返回 role、scene、hash、字符区间
或引文。Evidence ID 来自本次请求绑定的服务端目录，需要相邻多段时必须分别引用，不能合并。
服务端解析 ID 并注入权威 identity 后，组装一个 `compiler.prose-judge-report.v1`：

```json
{
  "schema_id": "compiler.prose-judge-report.v1",
  "role": "fidelity",
  "scene_id": "scene_1",
  "checklist_hash": "...",
  "render_hash": "...",
  "assessments": [
    {
      "check_id": "check_scene_1_001",
      "verdict": "pass",
      "evidence": [
        {
          "block_id": "block_scene_1_001",
          "start_char": 0,
          "end_char": 8,
          "text": "她推开仓库大门"
        }
      ],
      "rationale": "角色已实际进入仓库。"
    }
  ]
}
```

字段规则：

- Provider candidate 顶层和 assessment 均拒绝额外字段；Evidence ID 未知、重复或目录漂移使整份响应协议失败。
- `role`、`scene_id`、`checklist_hash`、`render_hash` 全部由服务端拥有，模型不抄写、计算或选择这些值。
- `role` 为 `fidelity`、`adversarial`、`coherence` 或 `arbiter`。
- 非 Arbiter 报告必须逐项覆盖整个 Checklist，顺序、check ID 和数量完全一致。
- `verdict` 为 `pass`、`fail`、`uncertain`。
- `rationale` 为 1–1000 code points，不得包含控制指令。
- 每项 evidence 最多 20 条；每条只能属于一个现有 block。
- `start_char` 为零基 Unicode code-point 索引，`end_char` 为半开区间且大于 start。
- `text` 必须逐字等于对应 block 的切片。
- 同一 block 内同一 text 出现多次时，坐标必须唯一确定目标 occurrence；服务端不猜测或自动重绑。
- 跨 block、合并句、删节号替代、改写、越界、错误 block 或正文不存在都使整份报告协议失败。
- `location_time` 的地点与故事时间分别判定；必需 Event 被否定、尚未发生、未来化或假设化时，地点正确也不能使该项通过。
- 各 check 独立判定，前置 Beat 缺失不得自动否定正文已实际实现的另一 Beat 或 Reveal。
- `causality_ordering` 使用明确的事件关系判断；“之前/之后/尚未”等事实优先于句子排列和正文自述。

Evidence 条件：

- `required + pass`：至少一条 evidence。
- `required + fail`：允许空 evidence，rationale 必须说明缺失或模态不足。
- `forbidden + fail`：至少一条 evidence。
- `forbidden + pass`：允许空 evidence，rationale 必须说明未发现违规。
- 任意 `uncertain`：evidence 可空，但必须说明无法裁决的具体歧义。

## Consensus 与 Arbiter

`compiler.prose-consensus-report.v1` 必须保存：

- scene、round、Checklist、Render、Council policy 和全部 Judge report hash。
- 每个 check 的角色 verdict、是否一致、是否进入 Arbiter。
- Arbiter request/report hash；没有争议时为 `null`。
- 每个 check 的最终 `pass | fail | uncertain` 和 `resolution_source=unanimous|arbiter`。
- Scene verdict `pass | fail | uncertain`。
- 失败 check IDs 和未解决 check IDs。

Arbiter request 只列出争议 check，但同时提供完整 SceneRender、完整 Checklist context 和这些 check 的全部角色 assessment。一轮内只有一次 Arbiter 调用。Arbiter 报告：

- 只允许返回争议 check。
- 必须保持争议 check 原顺序并完整覆盖。
- Evidence 使用与 Judge 相同的精确规则。
- 任一遗漏、额外 check、`uncertain` 或无效 evidence 都使 Scene verdict 为 `uncertain`。

Scene 只有全部 check 最终为 `pass` 时通过。任何 `fail` 或 `uncertain` 都触发可用的下一轮 Rewrite；Round 2 后进入 `semantic_rejected`。

## Rewrite 协议

Rewrite request 固定包含：

- 完整 Checklist 与当前 SceneRender。
- 当前 Consensus Report。
- 所有 failed/uncertain check 的 expectation、角色理由与合法 evidence。
- 所有已通过 check ID 与 expectation，作为必须保留的语义集合。
- Profile 与前一场已接受正文。
- `rewrite_round=1|2` 和剩余预算。

Rewrite 输出与 Writer 使用同一个 `scene-render-candidate.v1`，必须返回完整 Scene。不得返回 patch、删除区间、控制命令、接受决定或新的 Checklist。服务端规范化为 `rewrite_1` 或 `rewrite_2`，随后重新运行全部 check。

## Quality Critic 与 Polisher

Quality findings 的五个固定维度：

- `pov_voice_consistency`
- `scene_specificity`
- `dialogue_narration_naturalness`
- `dramatic_progression_pacing`
- `readability_editability`

每条 finding 包含 dimension、severity、精确 evidence 和 1–1000 code points 的问题描述，不包含改写正文。Polisher request 包含 Profile、语义已接受 SceneRender、Checklist 与 findings，输出完整 `scene-render-candidate.v1`。Profile 目标字符范围由模型用于自检，不是润色稿的服务端独立质量裁决；服务端只验证结构、绑定、lineage 与预算等硬协议，并由完整 Preservation Council 判定是否丢失语义。服务端只接收 Pairwise 的结构化偏好，并分别统计 Gold 准确率与镜像一致性。

润色稿必须重新运行完整 Semantic Council 和必要的单次 Arbiter。语义未通过即直接使用原稿形成 `accepted`，不调用 Pairwise Quality。

语义通过后，Quality Critic 对相同原稿/润色稿执行两次调用：

- 第一次匿名映射 `A=original, B=polished`。
- 第二次匿名映射 `A=polished, B=original`。

每次输出整体 preference 和五维 preference，取值为 `a | b | tie`。只有两次整体结果都映射为 polished，且没有任何维度在任一次映射为 original，才形成 `finalized_polished`；所有其他组合形成 `finalized_original`。模型看不到 original/polished、stage、Prompt version 或候选来源。

## NovelCandidate 与 CompileManifest

`compiler.novel-candidate.v1` 按 ScenePlan discourse order 保存最终 `accepted` SceneRender refs、合并正文、Scene 数和总字符数。缺少任一 Scene 时不得产生 NovelCandidate。

`compiler.compile-manifest.v1` 保存：

- 全部冻结输入与组件版本/hash。
- 每个 Scene 的 Checklist、各轮 Render、Judge、Consensus、Arbiter、Quality 与 accepted lineage。
- 每个 Scene 的最终状态、Rewrite 次数、调用数、usage、latency 和恢复信息。
- Shadow 总状态和未完成原因。

Manifest 只描述审计事实，不代替 TaskRun 终态或 AgentModelCall 原始证据。

## 八条权威 Trace

以下 Trace 使用最小字段切片表达完整裁决输入；未展开的 source hashes 均已冻结且匹配。

### Trace 1：显式实现 required Beat

- 输入 check：`required + beat_realization + required_on_pass`，expectation 为“调查者进入仓库”。
- Render：`block_scene_1_001="她推开仓库大门，走了进去。"`
- 三角色：均为 `pass`，evidence 精确指向“她推开仓库大门，走了进去”。
- Quality 路径中 Polisher 只改变句式，Preservation 通过，但两次 Pairwise 都为 tie。
- 转换：`draft_ready → semantic_reviewing → semantic_accepted → polishing → preservation_reviewing → quality_comparing → finalized_original`。
- 预期终态：`finalized_original`；不得 Rewrite，accepted 内容逐字等于 Writer 原稿。

### Trace 2：隐含但充分实现 required Beat

- 输入 check：`required + event_modality`，expectation 为“她最终决定选择东线”。
- Render：`她收起另外两张路线图，只把东侧那页压在掌下。`
- Fidelity=`uncertain`，Adversarial=`pass`，Coherence=`pass`，均提供其判断依据。
- Arbiter 结合上下文裁决 `pass`，证据定位整句。
- Polisher 改善节奏且不改变该隐含决定；Preservation 通过，两次 Pairwise 都选择 polished。
- 转换：`draft_ready → semantic_reviewing → semantic_accepted → polishing → preservation_reviewing → quality_comparing → finalized_polished`。
- 预期终态：`finalized_polished`；不因表达含蓄而 Rewrite。

### Trace 3：required Beat 缺失

- 输入 check：`required + beat_realization`，expectation 为“发现停摆的怀表”。
- Render 只写角色进入仓库，没有怀表。
- 三角色均返回 `fail`，evidence 为空，rationale 明确说明正文没有实现该 Beat。
- Rewrite 1 增加发现怀表的动作，完整复审全部通过；润色质量结果不一致并回滚。
- 转换：`semantic_reviewing → rewrite_1_pending → semantic_reviewing → semantic_accepted → polishing → preservation_reviewing → quality_comparing → finalized_original`。
- 预期终态：`finalized_original`，accepted 内容来自 Rewrite 1；不能因缺少引文把首轮合法 fail 判成协议错误。

### Trace 4：提前 Reveal

- 输入 check：`forbidden + reveal_control + required_on_fail`，expectation 为“不得揭露 killer_identity”。
- Render：`她还不知道，凶手其实就是鲍勃。`
- 至少 Adversarial 返回 `fail`，evidence 精确定位该句；其他角色若不同意则进入 Arbiter。
- 最终 check=`fail`。
- Rewrite 1 删除提前 Reveal 并通过完整复审；润色稿通过 Preservation 和双位置质量评审。
- 转换：`semantic_reviewing → rewrite_1_pending → semantic_reviewing → semantic_accepted → polishing → preservation_reviewing → quality_comparing → finalized_polished`。
- 预期终态：`finalized_polished`；首轮必须重写，文学质量分数不能放行。

### Trace 5：分歧且 Arbiter 仍 uncertain

- 输入 check：`required + scene_outcome`，expectation 为“双方建立临时信任”。
- Render：`她把钥匙放进他的掌心，却没有收起另一只手里的刀。`
- Fidelity=`fail`、Adversarial=`pass`、Coherence=`uncertain`。
- Arbiter=`uncertain`，说明交付钥匙与持刀形成无法消除的语义歧义。
- 该歧义在 Rewrite 1 和 Rewrite 2 中都未消除，三轮 Arbiter 均为 `uncertain`。
- 转换：Round 0 `→ rewrite_1_pending`，Round 1 `→ rewrite_2_pending`，Round 2 `→ semantic_rejected`。
- 预期终态：`semantic_rejected`；不得多数票放行。

### Trace 6：两轮 Rewrite 后仍失败

- Round 0 缺失 outcome，进入 Rewrite 1。
- Round 1 修复 outcome 但新增提前 Reveal，完整复审发现新问题并进入 Rewrite 2。
- Round 2 移除 Reveal，却把“已经决定”弱化为“可以考虑”，event modality 最终 `fail`。
- 转换：`rewrite_2_pending → semantic_reviewing → semantic_rejected`。
- 预期终态：`semantic_rejected`；不得第三次 Rewrite、额外采样或借用剩余调用预算。

### Trace 7：Polisher 改坏语义并回滚

- 原稿已 `semantic_accepted`。
- Polisher 为增强戏剧性增加尚未允许的凶手暗示。
- Preservation Council 对 reveal check 返回 `fail` 并给出精确引文。
- 转换：`polishing → preservation_reviewing → finalized_original`。
- 预期终态：`finalized_original`；原稿成为 `accepted`，不运行 Pairwise Quality，不把润色稿写入最终 NovelCandidate。

### Trace 8：Provider/Worker 故障

- N4.4 已成功产出 ScenePlanIR v2；N4.5 Writer 或 Judge 调用发生网络错误，或 Worker 在 Artifact 写入前失去 lease。
