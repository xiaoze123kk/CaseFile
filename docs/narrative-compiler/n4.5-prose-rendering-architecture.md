# N4.5 Prose Rendering 与 Judge Council 架构

## 文档状态

本文是 N4.5-00 的架构决策记录，冻结 N4.5 正文生成、语义评审、有限重写、文学润色与 Preview Shadow 的职责边界。字段级协议见
[`n4.5-agent-judge-protocol.md`](n4.5-agent-judge-protocol.md)，评测与资格协议见
[`n4.5-benchmark-qualification.md`](n4.5-benchmark-qualification.md)。

设计基线：

- 分支：`N4.5`。
- 起点：`31b54e6`。
- 输入权威：`compiler.scene-plan.v2`、`compiler.narrative-ir.v1`、`compiler.novel-profile.v2`。
- 第一版 Provider：DeepSeek。
- 运行模式：仅 `preview + prose_renderer_shadow=true`，默认关闭。
- 单 Scene Rewrite 上限：两轮。
- Judge 分歧：一次批量 Arbiter 后失败关闭。

N4.5-00 只冻结设计，不定义 Schema、Prompt、Fixture、ORM、迁移或运行时实现，也不产生 Provider 调用。

## 目标与非目标

N4.5 把 N4.4 已规范化的 ScenePlanIR v2 渲染为可审计的小说正文，并用模型理解自然语言、用服务端控制执行和证据完整性。它回答“这一场如何写成正文，以及正文是否忠实实现既定 ScenePlan”，不重新规划故事。

本阶段架构必须支持：

- 按叙事顺序生成 Scene 正文，并携带前一场已接受正文和结构化入站状态。
- 把 ScenePlan 确定性编译为逐项 Judge Checklist。
- 分离语义正确性与文学质量；质量不得抵消任何语义失败。
- 使用 Fidelity、Adversarial、Coherence 三种 Judge 能力和争议项 Arbiter。
- 最多两轮完整 Scene Rewrite，每轮后重新评审全部 Checklist。
- 润色后的完整语义保真复审，以及位置互换的盲评质量比较。
- 精确恢复、调用预算、证据哈希与 Shadow 失败隔离。

明确不包含：

- 修改 CaseFile、Canon、Exposure Plan、ScenePlan 或 Draft。
- 自动采用正文、Manuscript 编辑、前端、canonical 编译或发布。
- 从正文反向建立新的事实权威、SourceMap 或 Proposition DSL。
- 无限 Rewrite、逐 check Arbiter、滚动摘要 Agent、跨模型族 Council 或通用多 Agent 框架。
- 用确定性关键词、正则或 SMT 判断隐喻、决定、潜台词、人物心理或文学语义。

## 权威与组件边界

### 冻结输入

每个 Scene 的完整冻结输入由以下内容组成：

1. 完整 ScenePlanIR v2 及当前 Scene/Beat/State 切片。
2. 匹配的 NarrativeIR v1 对象与来源闭包。
3. 匹配的 NovelProfile v2。
4. 第一场为 `null`，其余场为前一场最终已接受 SceneRender 的全文与内容哈希。
5. Prompt、Schema、Model、Checklist policy、Council policy 和运行时版本。

这些输入的规范 JSON 与 RFC 8785 SHA-256 共同构成组件 fingerprint。上游 SceneRender、Profile、ScenePlan、NarrativeIR、Prompt、Model、Schema 或 Policy 任一变化，当前 Scene 和所有后续 Scene 的缓存全部失效。

### 确定性 Checklist Compiler

Checklist Compiler 属于纯领域层，只读取冻结输入并输出 `compiler.prose-judge-checklist.v1`。它负责：

- 为每个 Scene/Beat obligation、Event modality、Reveal、POV knowledge、Location/Time、因果顺序、重大新增剧情与 Scene outcome 生成稳定 check。
- 投影 Judge 必需的来源目录、入站/预期出站状态和约束。
- 分配稳定 check ID、顺序、极性与证据要求。
- 完整覆盖当前 Scene 的冻结语义要求。

Checklist Compiler 不回答正文是否通过，不调用 Provider，也不根据正文改变检查目录。模型不得添加、删除、合并、重排或改写 check。

### 生成组件

Writer、Rewrite 和 Polisher 都只产出正文候选：

- Writer 根据 Checklist、Scene context、Profile 和前一场正文生成初稿。
- Rewrite 根据完整 Checklist、当前正文、Consensus 失败项与已通过项生成完整新正文，不生成 patch。
- Polisher 只在语义已经通过后，根据 Quality Critic findings 生成完整润色稿。

三个组件都不拥有 Scene/Beat 身份、状态变化、控制流、接受决策、Artifact 身份或资格门槛。服务端分配 SceneRender stage、round、block ID、哈希和 lineage。

### Semantic Judge Council

Fidelity、Adversarial、Coherence Judge 都读取同一冻结 Checklist 与同一 SceneRender，并按 Checklist 原顺序返回评审：

- Fidelity 重点判断必需 Beat、Event、Outcome 是否真正发生，且模态、主体与对象正确。
- Adversarial 重点寻找提前 Reveal、知识越权、地点/时间漂移、错误因果和重大新增剧情。
- Coherence 重点判断隐含行为、潜台词、省略、上下文承接是否足以实现要求，避免误杀合法文学表达。

Judge 负责解释自然语言，不决定执行下一步。服务端负责输出结构、check 覆盖、顺序、引文原文、Unicode 区间、哈希和预算校验。

### Consensus 与 Arbiter

Council policy 冻结本轮启用的角色集合。N4.5-02 会在开发集上按既定消融规则，从 Fidelity-only、Fidelity+Adversarial、完整三角色中选择满足门槛且成本最低的 policy；选择规则已经冻结，Holdout 不参与选择。

对于启用的角色：

- 同一 check 的所有 verdict 一致时，Consensus 直接采用。
- verdict 不一致或任一角色为 `uncertain` 时，该 check 进入争议集合。
- 一轮内全部争议 check 合并为一次 Arbiter 调用。
- Arbiter 只裁决争议 check，不返回或改写非争议项，不重新评审整场。
- Arbiter 返回 `uncertain`、遗漏 check、证据无效或结构失败时，本轮 Scene verdict 为失败。

Consensus Engine 是确定性组件。任何 `fail` 或未解决的 `uncertain` 都阻止语义放行。

### Quality Critic

Quality Critic 只在语义通过后工作，负责生成文学质量 findings，并在润色后执行匿名 A/B 比较。它不得：

- 修改 Semantic verdict。
- 抵消失败的 Checklist 项。
- 指示服务端跳过 Preservation Council。
- 依据候选身份、长度或版本名偏好某一正文。

### 持久化权威

运行时接入阶段继续沿用现有权威：

- `CompileArtifact` 保存不可变领域产物及内容哈希。
- `AgentStepRun` 保存一个组件的执行、输入、上游哈希、用量和诊断。
- `AgentModelCall` 保存一次真实模型调用、模型/Prompt、原始响应、解析结果、用量与延迟。
- `TaskRun` 保存 CompileRun 执行切片和最终终态。

不得新增重复表达这些职责的通用 Result、Run 或 Call 表。

运行时组件 ID 冻结为：`prose_checklist`、`prose_writer`、
`prose_fidelity_judge`、`prose_adversarial_judge`、`prose_coherence_judge`、
`prose_arbiter`、`prose_rewrite`、`prose_quality_critic`、`prose_polisher` 与
`prose_manifest`。确定性组件可以没有 AgentModelCall，但仍必须以 AgentStepRun 记录输入、
上游哈希、版本和终态。

N4.5 使用 N4.0 已预留的 Artifact kind，不新增平行产物系统：

| Artifact kind | Artifact key 规则 | 内容 |
|---|---|---|
| `scene_context` | `compiler.scene_context.{scene_id}` | `compiler.prose-judge-checklist.v1` |
| `scene_render` | `compiler.scene_render.{scene_id}.{stage}` | 各轮 `compiler.scene-render.v1` |
| `validation_report` | `compiler.validation_report.{scene_id}.semantic_{round}.{role}` | 单个 Judge/Arbiter report |
| `validation_report` | `compiler.validation_report.{scene_id}.semantic_{round}.consensus` | 本轮 Consensus report |
| `validation_report` | `compiler.validation_report.{scene_id}.quality.findings` | Quality findings |
| `validation_report` | `compiler.validation_report.{scene_id}.preservation.consensus` | 润色保真 Consensus |
| `validation_report` | `compiler.validation_report.{scene_id}.quality.pairwise` | 双位置质量报告 |
| `novel_candidate` | `compiler.novel_candidate` | 完整最终正文 |
| `compile_manifest` | `compiler.compile_manifest` | 完整 N4.5 lineage 与 Shadow 状态 |

`stage` 只能是 `writer`、`rewrite_1`、`rewrite_2`、`polished`、`accepted`。
同一 CompileRun 内 key 唯一；Artifact 内容不可变并绑定产生它的 AgentStepRun。

## 串行数据流

```text
ScenePlanIR v2
  → Checklist
  → Writer
  → Semantic Round 0
  → Rewrite 1?
  → Semantic Round 1
  → Rewrite 2?
  → Semantic Round 2
  → Quality Critic
  → Polisher
  → Preservation Council
  → Mirrored Pairwise Quality
  → Final Scene
  → Next Scene
```

Scene 按 `discourse_order` 严格串行。只有 `finalized_original` 或 `finalized_polished` 的正文能够成为下一场的 `previous_scene_render`。`semantic_rejected`、`blocked_precondition` 或 `inconclusive_infrastructure` 都终止 N4.5 Shadow 链路；后续 Scene 不运行，因为缺少权威的前一场正文。

每轮 Semantic Review 都重新评审全部 Checklist。Rewrite 不能把原来通过的 check 当作永久通过，也不能只修复、只复查失败项。

## Scene 状态机

主状态机：

```text
pending
→ checklist_ready
→ draft_ready
→ semantic_reviewing
→ rewrite_1_pending | semantic_accepted
→ semantic_reviewing
→ rewrite_2_pending | semantic_accepted
→ semantic_reviewing
→ semantic_rejected | semantic_accepted
→ polishing
→ preservation_reviewing
→ quality_comparing
→ finalized_polished | finalized_original
```

状态转换规则：

| 当前状态 | 条件 | 下一状态 |
|---|---|---|
| `pending` | 输入闭包与 fingerprint 合法 | `checklist_ready` |
| `checklist_ready` | Writer SceneRender 合法 | `draft_ready` |
| `draft_ready` | 开始本轮完整 Council | `semantic_reviewing` |
| `semantic_reviewing` | Round 0 失败 | `rewrite_1_pending` |
| `rewrite_1_pending` | Rewrite 1 SceneRender 合法 | `semantic_reviewing` |
| `semantic_reviewing` | Round 1 失败 | `rewrite_2_pending` |
| `rewrite_2_pending` | Rewrite 2 SceneRender 合法 | `semantic_reviewing` |
| `semantic_reviewing` | Round 2 失败 | `semantic_rejected` |
| `semantic_reviewing` | 任一 Round 通过 | `semantic_accepted` |
| `semantic_accepted` | Quality findings 合法并启动 Polisher | `polishing` |
| `polishing` | 润色稿合法 | `preservation_reviewing` |
| `preservation_reviewing` | 语义失败或不确定 | `finalized_original` |
| `preservation_reviewing` | 语义通过 | `quality_comparing` |
| `quality_comparing` | 两次盲评一致接受且无维度回退 | `finalized_polished` |
| `quality_comparing` | 其他结果 | `finalized_original` |

`blocked_precondition` 与 `inconclusive_infrastructure` 是旁路终态：

- `blocked_precondition` 只能在首次模型调用前产生，表示缺少 ScenePlan v2、Profile v2、Provider 绑定或输入闭包。
- `inconclusive_infrastructure` 可以从任一需要 Provider、解析、持久化或有效 lease 的状态产生。
- 协议失败、空结构化响应和引文校验失败属于 inconclusive，不伪装成语义失败。
- 模型给出的合法 `fail` 或 `uncertain` 经 Consensus/Arbiter 处理后属于语义失败。

## 调用预算

单 Scene 的最坏调用预算固定为 23：

| 组件 | 最大调用 |
|---|---:|
| Writer | 1 |
| 三轮 Semantic Council | 9 |
| 三轮 Arbiter | 3 |
| Rewrite | 2 |
| Quality Critic findings | 1 |
| Polisher | 1 |
| Preservation Council + Arbiter | 4 |
| 双位置 Quality Pairwise | 2 |
| 合计 | 23 |

三个最坏路径复算：

| 路径 | 算式 | 最大调用 |
|---|---|---:|
| 0 次 Rewrite | Writer 1 + Round 0 `(3+1)` + Critic 1 + Polisher 1 + Preservation `(3+1)` + Pairwise 2 | 13 |
| 1 次 Rewrite | Writer 1 + Round 0 `(3+1)` + Rewrite 1 + Round 1 `(3+1)` + Critic 1 + Polisher 1 + Preservation `(3+1)` + Pairwise 2 | 18 |
| 2 次 Rewrite | Writer 1 + 三轮 `(3+1)` + Rewrite 2 + Critic 1 + Polisher 1 + Preservation `(3+1)` + Pairwise 2 | 23 |

计算按完整三角色与每轮都触发 Arbiter 的最坏情况冻结。开发集选出更小 Council policy 后可以少调用，但创建 CompileRun 时仍以 23/Scene 作为硬上限，不得把节省的预算转移为额外 Rewrite、额外采样或逐 check 仲裁。

每次调用固定 `max_turns=1`。协议错误、语义失败和空结构化响应不得透明重试。网络、Provider 或持久化故障必须保存已发生调用，并使当前 N4.5 Shadow 进入 `inconclusive_infrastructure`。

## 恢复、取消与 fencing

成功调用只有在以下 fingerprint 全部相同时才能恢复复用：

- CompileRun 与 Scene identity。
- Component、runtime、Prompt、Schema、Model 与 Council policy version。
- ScenePlan、NarrativeIR、Profile、Checklist 和前一场最终正文哈希。
- 当前 SceneRender、round、stage 和全部上游 Artifact hash。

恢复必须保持原调用的 usage、latency、raw response 与输出哈希，不创建伪造的零成本调用。任何 fingerprint 不同都重新执行当前及后续组件。

取消和 lease 检查只发生在组件边界；不得在单次 Provider 调用、单个 Judge 报告解析或 Artifact 事务中间强制切断。失去 lease 的 Worker 不得写 Step、Call、Artifact 或终态。成功 Artifact 的精确复用不授予跨 TaskRun、跨 revision 或跨 Profile 的通用缓存权。

## Preview Shadow 语义

N4.5 第一版只允许显式 `preview + prose_renderer_shadow=true`：

- 默认值为 `false`。
- 必须绑定 DeepSeek Provider、精确 Profile v2 与 ScenePlanIR v2。
- 不写 Draft，不自动采用正文，不改变 Canon 或 Exposure。
- N4.5 成功只附加 Shadow Artifact 与诊断；既有 N4.4 产物继续是主编译权威。
- N4.5 blocked、inconclusive 或 semantic rejected 都记录真实状态，但不得把已成功的 N4.4 CompileRun 改为失败。
- API/读模型只能把 N4.5 状态投影为明确的 Shadow 子结果，不得把 `finalized_*` 表达为作者已采用。

资格通过只表示显式 Preview Shadow 可用，不自动改变默认值，也不授权 canonical、自动采用或必经执行。

## 冻结与延期边界

N4.5-00 冻结组件、字段语义、状态机、预算、失败关闭、Benchmark 选择规则和资格门槛。N4.5-01 只能把这些决策实现为跨语言契约和纯领域规则，不得重新定义职责。

跨模型族 Council、24×5/10 Stability、滚动摘要、Manuscript 生命周期、前端和默认启用均不属于 N4.5-00 至 N4.5-08 的交付范围。
